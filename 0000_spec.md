# Surmount spec spec

> v0.1.0 - 20260831
> Form rules for numbered Surmount specs (spec 0)

## 1. Scope

This document is the spec spec for Surmount miscellaneous specifications. It defines how specification documents in this repository SHALL be written, named, versioned, cited, and checked for form.

### 1.1 Documents in scope

The following documents SHALL conform to this document:

1. Every file matching `NNNN_descriptive_name.md` in the repository root, where `NNNN` is a four digit decimal prefix. Numbered specification files live only at the repository root as a flat set of files. They SHALL NOT be nested under a subdirectory such as `specs/` or `docs/specs/`. That flat root layout is the same spirit as the bitcoin/bips repository: numbered proposals at the root, not under a nested proposals folder.
2. This document (`0000_spec.md`), which SHALL obey its own rules.

### 1.2 Documents out of scope

The following are not specification documents under this document:

1. `README.md` and other repository orientation files. They SHOULD use pure ASCII and American English when practical, but need not satisfy every clause here.
2. `UNLICENSE.md`, `LICENSE`, `LICENSE.md`, and equivalent license files. Standard legal text is excluded from style, spelling, list form, and hyphenation rules that would force rewriting canned license prose. License files SHOULD remain pure ASCII when the chosen license text allows it.
3. Scripts, Nix expressions, word lists, hooks, Lean sources, and other tooling that is not markdown. Tooling may enforce this document; it is not itself a specification under these style rules.

### 1.3 Status of this document

This document is normative for document form. It does not define product behavior, wire formats, or APIs except as they appear inside other specs.

Concise American Technical English is specified in `0005_CATE.md`. This document does not restate CATE. Authors SHALL follow that specification when writing numbered specifications in this repository.

## 2. Normative references

The following documents are indispensable for the application of this document. For undated references, the latest edition applies. Local copies under `ref/` are preferred when present (see Clause 12).

1. Semantic Versioning 2.0.0 (SemVer). Local path when present: `ref/semver`.
2. RFC 2119, Key words for use in RFCs to Indicate Requirement Levels. Local path when present: `ref/rfc2119`.
3. ECMA-48 / ISO/IEC 6429 and related terminal control standards, as cited by individual product specs such as DOGE, when those specs require them. Local paths under `ref/` when present.
4. Concise American Technical English (CATE), Surmount specification `0005_CATE.md`. Authors SHALL follow that specification when writing numbered specifications in this repository. This document does not restate CATE.

If a `ref/` path is empty or not yet populated, authors SHALL still cite the public standard by title and identity, and SHALL add or update the `ref/` entry under Clause 12 when the external reference process is completed.

## 3. Definitions

### 3.1 Normative specification

A numbered `NNNN_descriptive_name.md` document that states mandatory requirements for an implementation, format, or other subject, and is not labeled as informative only.

### 3.2 Document that is informative only

A document that provides background, history, or guidance without mandatory implementation requirements. It SHALL say near the top that it is informative only.

### 3.3 Publication

The act by which the repository operator declares a specification version shipped. Working text is not publication until the operator says so. By operator order, numbered specifications in this repository other than `0001_DOGE.md` carry version line 0.1.0. Digital Octal Graphical Emissive (DOGE) remains 1.0.0. That 0.1.0 line is the current version on disk. It is not a fake history of shipped 0.x releases. First publication SHALL NOT be required to be 1.0.0 for those files.

### 3.4 Repository operator

The person or role that controls publication decisions for this repository.

### 3.5 External reference tree

The `ref/` directory, holding public standards this repository cites so readers and tools can open the exact text meant without hunting the web: either git submodules from each standard's canonical git source that the publisher maintains (Form 1), or official publisher artifact pins (PDF, plain text, or similar) committed directly in this repository's git tree with `SOURCE.md` metadata (Form 2). Hyperlinks to publisher pages still matter as publisher links. See Clause 12.

## 4. Normative language

### 4.1 RFC 2119 requirement keywords

1. Specs SHALL use the requirement keywords defined in RFC 2119 in the RFC 2119 sense: MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY, and OPTIONAL.
2. Specs SHALL cite RFC 2119 (and the local `ref/` copy when present) in Normative references or an equivalent early section when they use those keywords.
3. Keywords are not case sensitive under RFC 2119; this repository RECOMMENDS writing them in uppercase in normative clauses so readers can scan for requirements.
4. Specs SHALL NOT invent a private mapping that weakens or redefines these keywords (for example, telling authors not to use MUST when RFC 2119 MUST is intended).

### 4.2 Normative versus informative text

1. Background, history, design reasoning, examples, notes, acknowledgments, and changelog narrative are informative. They explain context; they are not requirements by themselves.
2. Requirements use the RFC 2119 keywords (MUST, SHALL, SHOULD, MAY, and the rest listed in Clause 4.1) in the RFC 2119 sense. A sentence that states a requirement SHALL use those keywords so readers can tell it is normative.
3. Informative material SHOULD be titled or opened so a reader can tell it is not a requirements section. Examples of clear titles: "Algorithm selection reasoning", "Background (informative)", or an opening sentence that the subsection is informative.
4. Authors SHALL NOT invent private jargon that redefines requirement levels or invents a parallel vocabulary for rules that sound like MUST. Use ordinary American English plus RFC 2119 keywords for requirements.
5. If a requirement sentence appears inside an otherwise informative section, the RFC 2119 keyword still makes that sentence normative. Prefer keeping requirements in clearly normative sections and leaving informative sections free of mandatory rules.
6. Open questions, behavior the implementation defines, and undefined behavior SHALL be labeled as such and SHALL NOT be mixed unmarked into mandatory requirements.

## 5. Document structure

### 5.1 Title and version line

1. The first heading SHALL be a single top level markdown title (`# ...`) naming the specification.
2. Immediately under the title, a blockquote line SHOULD give the version and date.
3. The version line SHOULD use Semantic Versioning with an optional leading `v` and a date. By operator order the current line for numbered specifications other than `0001_DOGE.md` is:

```text
> 0.1.0 - YYYYMMDD
```

or:

```text
> v0.1.0 - YYYYMMDD
```

`0001_DOGE.md` remains `v1.0.0`. Changelog history MAY record that a 1.0.0 line existed.

4. A one line subtitle in the same blockquote, or on the line after the version line, MAY state the document role (for example "Form rules for numbered Surmount specs (spec 0)").

### 5.2 Version and date format

1. Version strings SHALL follow Semantic Versioning 2.0.0 (MAJOR.MINOR.PATCH). See Clause 13.
2. Dates in version lines and changelog headings SHALL use `YYYYMMDD` (four digit year, two digit month, two digit day, no separators).
3. In running prose, dates MAY use `YYYYMMDD` or `YYYY-MM-DD`. A single spec SHOULD pick one prose form and keep it consistent.
4. Specs SHALL NOT invent a fake history of shipped 0.x releases for work that was never published. First publication of a specification SHALL be version 1.0.0. Changelog entries SHOULD use real SemVer headings once versions are assigned; they SHALL NOT label intermediate snapshots as shipped version numbers that were never released.

### 5.3 Section skeleton

Normative specs SHALL use numbered section headings of the form `## N. Title` and `### N.M Title` (and deeper levels as needed).

Recommended order for a normative specification:

1. Scope
2. Normative references (if any)
3. Definitions (if any)
4. Core clauses (requirements, tables, algorithms)
5. Required Conformance clause (see Clause 14)
6. Changelog (required after first publication; recommended earlier)
7. Copyright or License
8. Acknowledgments (optional)

Documents that are informative only need not include a Required Conformance clause as a requirements section, but SHALL state near the top that the document is informative only.

### 5.4 Lists

1. Outside fenced code blocks, specs SHALL NOT use markdown bullet list markers (`-`, `*`, or `+` at the start of a list item).
2. Specs SHALL use numbered lists (`1.`, `2.`, ...) or lettered lists (`a.`, `b.`, ... / `A.`, `B.`, ...) for enumerations in prose.
3. Table rows and markdown headings are not list markers and are allowed.

## 6. Character set and writing system

### 6.1 Pure ASCII

1. The entire specification file SHALL consist only of ASCII bytes.
2. Allowed bytes are:
	a. Printable ASCII in the range 0x20 through 0x7E.
	b. Horizontal tab 0x09.
	c. Line feed 0x0A.
3. Carriage return 0x0D SHALL NOT appear. Files SHALL use line endings that use LF and never CR.
4. Other control characters (including NUL) SHALL NOT appear.
5. Unicode punctuation SHALL NOT appear. Forbidden examples include em dashes, en dashes used as punctuation, smart quotation marks, and the Unicode ellipsis character. Use ASCII `-`, straight quotes, and `...` (three periods) instead.

### 6.2 American English

1. Prose SHALL use American English spelling and wording (en_US).
2. On first use of an acronym that the expected audience might not know, specs SHOULD expand the acronym and MAY give the short form in parentheses.
3. Proper nouns and stable external identifiers SHALL keep their upstream spelling and capitalization (for example ECMA-48, Floyd-Steinberg, SemVer).

### 6.3 Spelling checkability

Documents in scope SHALL remain checkable by the repository validator for spelling, character set, list form, hyphenation, and whitespace rules defined here. Domain terms that are correct but absent from a stock en_US dictionary MAY be listed in the repository spelling word list so that validation stays green without weakening the American English rule.

### 6.4 Line wrapping (not wrapped to a column)

1. Spec prose SHALL NOT be wrapped to a column. Readers configure soft word wrap in their editor or viewer.
2. Prefer one physical line per paragraph and per list item body.
3. Deliberate line breaks remain for structure: blank lines, headings, list items (one item per line), tables, fenced code blocks, and blockquotes as blocks. The item text of a list entry SHOULD NOT wrap in the middle of a sentence onto a following physical line unless structure requires a nested block.
4. The Lean checker enforces a heuristic for wrapping to a column on numbered specifications outside fenced code and tables: two consecutive body lines that are not empty where the first does not end a sentence or closed structure (does not end with `.`, `!`, `?`, or `:`) and the second continues with a lowercase letter. Full sentences that end with `.` on short lines still pass. Fenced code and table rows are exempt.
5. Informative author tips (not a change to the algorithm in item 4): a common trip is a paragraph split in the middle of a sentence so the next physical line starts with a lowercase letter. Fix by joining that paragraph into one physical line (soft wrap in the editor). A short full sentence that ends with `.` on its own line, then a new sentence starting with a capital, is fine. Nested list structure and blank line paragraph breaks are not wraps to a column. Human oriented examples also appear in `README.md` under Validation.

### 6.5 Indentation (tabs)

1. Leading indentation (whitespace from the start of a line before content) SHALL use tab characters (0x09) only, never space (0x20).
2. Spaces MAY appear in the middle of a line in prose and inside table rows (for example `| foo | bar |` cell padding). Those spaces are content or table formatting, not leading indentation.
3. Nested markdown lists and other nested blocks SHALL indent with tabs (one tab per nesting level is the usual form).
4. Empty lines may be empty. Trailing whitespace is forbidden separately (Clause 6.6).
5. Language and format exceptions for source files in this repository that are not specifications: Lean sources MUST use spaces because the Lean 4 parser rejects tab indentation. YAML workflow files use spaces because common YAML tooling rejects tab indentation. Those exceptions apply to tooling files checked by the pure Nix whitespace check across the project; numbered specification markdown remains under the tab rule.

### 6.6 Trailing whitespace

1. Lines SHALL NOT contain trailing space or tab characters before the line feed.
2. The Lean checker enforces this on numbered specifications. The pure Nix flake check enforces it on text files owned by the project (see Clause 17 and `README.md`).

## 7. Hyphenation and identifiers in prose

1. Prefer ordinary English over hyphenated compounds. People who are not writing legal captions rarely hyphenate. Do not write modifiers such as `high-assurance`, `best-effort`, `self-improving`, `lock-free`, or `safety-critical`. Do not "fix" them by deleting the hyphen and leaving the same two words (`lock free`, `non markdown`, `must like`, `LF only`). Rephrase so a person would actually say it. `high assurance` may stay when it already reads as English. `3 bit`, `8 bit`, `24 bit`, and `high contrast` may stay. Say `tooling that is not markdown` rather than `non markdown tooling`. Say `tries that do not use locks` rather than `lock free tries`. Say `bootstrapped Slake that fully typechecks` rather than `fully type checking Slake`. The Lean `spec_check` leftover unstack list in `0005_CATE.md` is a floor for those leftover pairs; authors still SHALL rephrase other leftover pairs the checker does not name.
2. A lowercase token with two or more hyphens (three or more segments), for example `foo-bar-baz`, SHALL NOT appear in prose outside fenced code blocks and inline code spans. That mechanical ban is a floor. It does not license a single hyphen in prose when a rephrased form works, and it does not license deleting the hyphen and leaving the same two words.
3. Keep a hyphen in prose only when the token is a filename, a URL, a code identifier, or an official designation that is spelled with a hyphen (for example ITU-T, Floyd-Steinberg, ECMA-48, ISO/IEC). The mechanical checker still allows a single hyphen; authors still SHOULD use spaces.
4. Proper names and stable external identifiers MAY keep their canonical hyphens (for example Floyd-Steinberg, ECMA-48, ISO/IEC, ITU-T).
5. Filenames, URLs, and code identifiers inside inline code or fenced blocks are outside the prose hyphenation ban. The tool name `pre-commit` MAY stay as the tool name.

## 8. Precision

1. Terms with special meaning SHALL be defined before use or collected in a Definitions section.
2. Normative facts SHALL prefer exact values, ranges, and enumerations over vague language ("about", "roughly", "and so on") when implementers need a definite answer.
3. Behavior that the implementation defines, undefined behavior, or deliberately open behavior SHALL be called out with those words or in a clearly titled Open questions section.
4. Specs SHALL NOT leave silent gaps on values, units, or states that a conforming implementer needs in order to interoperate.

## 9. Units and quantities

1. Bit and byte widths in prose SHOULD be written with a space between the number and the unit word when used as adjectives or measures: `3 bit`, `8 bit`, `24 bit`. Do not treat this as a ban on `3-bit` in external quotations inside code fences.
2. Prefer unambiguous numeric dates as in Clause 5.2.
3. Use clear units for physical or logical quantities. Do not switch unit systems silently inside one spec.

## 10. Tables, code, and figures

1. Fixed enumerations of values (palettes, code points, parameter maps) SHOULD be given as markdown tables.
2. Fenced code blocks MAY present algorithms, examples, and ASCII diagrams.
3. Specs SHALL NOT embed binary image assets. External links to figures are discouraged in core normative clauses; if used, the normative content SHALL still be understandable from the text and tables alone.
4. ASCII diagrams inside fenced blocks MAY be used sparingly when they clarify structure.

## 11. File naming, numbering, and citation

### 11.1 File names and location

1. Specification files SHALL be named `NNNN_descriptive_name.md`.
2. `NNNN` is a four digit decimal prefix, padded on the left with zeros (for example `0000`, `0001`).
3. `0000` is reserved for this document (the Surmount spec spec).
4. `descriptive_name` SHALL use ASCII letters, digits, and underscores only. Filenames that use hyphens in the basename SHALL NOT be used for specs.
5. Numbered specification files SHALL live only in the repository root. Specs SHALL NOT be placed under nested directories (for example `specs/`, `docs/specs/`, or similar). See Clause 1.1.
6. Once a specification number has been published in the repository, that number SHALL NOT be reused for a different document. Do not renumber published specs.

### 11.2 Citation of other Surmount specs

1. Other specifications in this repository SHOULD be cited by file name and title, and MAY include a version string (for example `0001_DOGE.md`, Digital Octal Graphical Emissive (DOGE) Color Specification, 1.0.0).
2. When citing a specification that has not been published yet, do not invent a shipped version number for work the operator has not declared published.

### 11.3 Citation of external standards

1. External standards SHOULD be cited with enough identity for a reader to find them: title, issuing body when known, and version or year when relevant.
2. When this repository keeps a local copy under `ref/`, the citation SHOULD also name that path (for example `ref/semver`, `ref/rfc2119`).

### 11.4 Markdown path links in this repository

1. Markdown links that reference any material present in this repository SHALL resolve to a path that exists. That includes relative links, paths under `ref/`, sibling `.lean` files next to numbered specifications, and other numbered specification files.
2. Lean SHALL check that rule so the link graph among those path targets is consistent with files that exist.
3. The check SHALL scan numbered specification files matching `NNNN_descriptive_name.md` at the repository root for markdown links of the form `[text](target)`. It SHOULD also scan `README.md`.
4. The check SHALL skip targets that begin with `http://` or `https://`.
5. Remaining targets SHALL be resolved relative to the file that contains the link, or relative to the repository root. The check SHALL fail when the resolved path does not exist.
6. A target that is only a fragment (`#heading`) is the same file and SHALL NOT fail for a missing path. A target that combines a path and a fragment SHALL be checked on the path before the fragment.
7. This floor does not parse every HTML `href`. It does not parse reference style markdown links.

## 12. External references (`ref/`)

### 12.1 Purpose

1. `ref/` holds the external standards this repository cites (Semantic Versioning, RFC 2119, ECMA and ISO terminal standards, and similar) so readers and tools can open the **exact** text meant without hunting the web.
2. Hyperlinks to publisher pages still matter (and often predate git and even some of the specs). Canonical URLs SHALL remain in each Form 2 entry's `SOURCE.md` file and in each Form 1 sibling `.SOURCE` file, and SHOULD appear in citations.
3. Local copies under `ref/` freeze what this repository reviewed and checksummed or pinned in git. They do not replace the publisher page as the public home of the standard.

### 12.2 Process rule (binding)

1. Any external specification this repository cites MUST be present under `ref/` in one of the two forms in this clause.
2. **Form 1: Canonical git that the publisher maintains.** When a cited standard has a **canonical git repository maintained by the publisher** (any host: GitHub, GitLab, a host you run yourself, or other; NOT assumed to be GitHub), authors SHALL add it under `ref/` as a git submodule from that publisher git URL and pin a tag or commit. Example: Semantic Versioning under `ref/semver`.
3. **Form 2: No canonical git that the publisher maintains.** When the publisher does not maintain a canonical git repository for that standard (common for standards from before git and from the PDF era), or when official git is not the authoritative publication form, Form 2 is the **intended** process (not a fallback failure). Authors SHALL:
	1. Document that fact in `ref/README.md` for the entry (no publisher git; what is used instead).
	2. Keep a **local copy** of the specific official publisher artifact needed under `ref/<short_name>/`, committed **directly in this repository's git tree** as ordinary files (**not** a submodule), obtained from the most canonical official source the publisher provides.
	3. Record canonical hyperlink(s), retrieval date, checksum, and edition or version in a pure ASCII `SOURCE.md` file under that directory. Publisher hyperlinks still matter as publisher links; the local copy freezes the reviewed bytes.
	4. Note license, copyright, or republication status for the entry in `ref/README.md` (detail MAY remain in `SOURCE.md`).
	5. State reasoning in `ref/README.md`: why direct tree copy instead of submodule (no publisher git; durable local pin of the exact official artifact; hyperlinks remain for the living publisher location; no invented fake git remotes). That form **does** satisfy this clause. Examples: RFC 2119 (RFC Editor plain text under `ref/rfc2119`), ECMA-48 (Ecma International PDF under `ref/ecma48`), and ITU-T T.416 (ITU free PDF under `ref/itu_t416`; identical text also published as ISO/IEC 8613-6).
4. Authors SHALL NOT invent a random third party mirror or community reformat as "canonical git." Prefer honesty about what the publisher actually maintains.
5. Authors SHOULD prefer Form 1 when the publisher truly maintains git for that standard, and SHOULD prefer Form 2 when that is what the publisher ships. Standards from before git and from the PDF era (RFC 2119, ECMA-48, ITU-T T.416, and similar) are expected to use Form 2 unless the publisher later maintains real canonical git for that standard.
6. Directory names under `ref/` SHOULD be short, stable, and lowercase (examples: `semver`, `rfc2119`, `ecma48`, `itu_t416`).
7. Authors SHALL NOT edit upstream files inside submodules or inside pinned official artifacts. Specs cite a version, tag, commit, or `SOURCE.md` checksum. Update the pin when the cited version must change.
8. Process detail for operators and agents, including per-entry license notes and "Why we pin this way," is described in `ref/README.md`. A short summary also appears in the repository root `README.md`.

### 12.3 Present initial references

The following are expected early `ref/` entries for this repository when populated. Each form below is valid under Clause 12.2:

1. Semantic Versioning (`ref/semver`) - Form 1 git submodule of the SemVer project's canonical repository that the publisher maintains, when present.
2. RFC 2119 (`ref/rfc2119`) - Form 2 official RFC Editor plain text pin committed directly in this repository's git tree with `SOURCE.md` when present. There is no canonical git repository that the publisher maintains for this historic RFC that this process treats as authoritative; third party copies are not canonical.
3. ECMA-48 and related ISO/IEC terminal control references as used by DOGE and similar specs, when available under `ref/` - Form 2 official Ecma International PDF pin committed directly in this repository's git tree with `SOURCE.md` for ECMA-48 (`ref/ecma48`) when present. Community reformats are not the Ecma publisher source.
4. ITU-T T.416 / ISO/IEC 8613-6 (`ref/itu_t416`) - Form 2 official ITU free PDF pin (Recommendation T.416, 03/93; identical text also published as ISO/IEC 8613-6) committed directly in this repository's git tree with `SOURCE.md` when present. There is no canonical git that the publisher maintains for this Recommendation. DOGE cites this standard for extended color models.

Population of `ref/` may be performed by a separate effort. Specs MAY be written citing these paths before the directories exist; the paths remain the documented local locations.

### 12.4 Adding or updating a citation

When a specification gains a new normative or strongly recommended external citation, authors SHALL:

1. Add or update the corresponding `ref/` entry under Clause 12.2: either a Form 1 git submodule from the standard's canonical git source that the publisher maintains, or a Form 2 official publisher artifact pin with `SOURCE.md` committed directly in this repository's git tree, as fits what the publisher actually provides.
2. Cite both the public identity of the standard (including publisher hyperlink when useful) and the local `ref/` path when the path exists.
3. Avoid treating an empty or not yet populated `ref/` path as a reason to drop the public citation. Document the intended path and complete the pin when the process allows.
4. Authors SHALL NOT delete a valid pin solely to force a different form without operator direction.
5. Existing pins remain. New pins are added when the cited artifact is present under `ref/`.
6. A Form 2 PDF pin SHALL include `SOURCE.md`. A permission note for republication of those PDFs SHALL be recorded when the operator writes that note. Until that note exists, residual SHALL name that it is not yet written.

## 13. Versioning (Semantic Versioning and publication)

### 13.1 SemVer is real Semantic Versioning

1. Specification version numbers SHALL follow Semantic Versioning 2.0.0: MAJOR.MINOR.PATCH.
2. Specs SHALL cite SemVer (and `ref/semver` when present).
3. A change that makes previously conforming implementations nonconforming SHALL raise MAJOR and MAY reset MINOR and PATCH to 0 as SemVer describes.
4. A backward compatible addition or clarification SHOULD raise MINOR (and MAY reset PATCH to 0) as SemVer describes.
5. A backward compatible fix that does not add feature surface SHOULD raise PATCH only.

### 13.2 First publication and honesty about history

1. The repository operator controls when a specification is published.
2. Specs SHALL NOT invent pretend shipped releases for work that was never published.
3. By operator order dated 20260831, numbered specifications other than `0001_DOGE.md` carry version line 0.1.0. First publication SHALL NOT be required to be 1.0.0 for those files. Digital Octal Graphical Emissive (DOGE) remains 1.0.0.
4. Specs MAY carry a SemVer version line (Clause 5.1) without special draft status wording. Agents and authors SHALL NOT invent fake version history or claim publication the operator has not declared.
5. Changelog entries SHOULD use SemVer version headings when versions are assigned. They SHALL NOT label snapshots as shipped version numbers that were never released. Changelog history MAY record that a 1.0.0 line existed.

### 13.3 MAJOR 0

The current version line 0.1.0 on numbered specifications other than `0001_DOGE.md` is operator order, not a fake 0.x release train. Digital Octal Graphical Emissive (DOGE) remains 1.0.0. Changelog history MAY record that a 1.0.0 or later line existed.

## 14. Required Conformance clause

This clause states what every normative Surmount specification is required to include inside its own document. It is not the checklist for whether a document meets this document (the form rules in 0000); that checklist is Clause 19.

1. Every normative specification SHALL include a section that states how an implementation or document conforms to that specification (what has to be true to claim conformance).
2. That section SHOULD be titled in plain English so readers can find it (for example "Conformance" or "Conformance requirements").
3. Documents that are informative only SHALL say they are informative only near the top of the file and need not define implementation conformance.
4. Authors SHOULD NOT use the same heading title for (a) the conformance requirements inside that specification for implementers of that spec and (b) any checklist about conforming to this document (the form rules in 0000), when both appear. Prefer distinct titles such as "Conformance" for (a) and leave form rule checklists to this document (Clause 19).

## 15. Change control

1. After first publication, every normative specification SHALL include a Changelog section.
2. Each published revision SHALL add a changelog entry headed with the SemVer version and date form from Clause 5.2 (for example `### 1.1.0 - 20260815`).
3. Changelog entries SHOULD summarize normative changes in plain language. Informative edits MAY be noted briefly or omitted when trivial.
4. Version numbering follows Clause 13.
5. Specs SHOULD keep a short changelog with SemVer headings once versions are assigned, without fake release numbers for work that was never shipped.

## 16. Copyright and license

1. Every specification SHALL include a Copyright or License section, or an explicit statement that the repository license applies to the document.
2. Unless a specification states otherwise, the repository Unlicense (public domain dedication) applies.
3. License sections MAY quote or summarize the Unlicense. They SHALL NOT contradict the repository license without an explicit, visible alternate terms statement.

## 17. Machine validation

### 17.1 Authoritative checkers

1. The authoritative automated checker for mechanical form rules on numbered specifications implied by this document is a Lean program, packaged and run through the repository Nix flake as the sole software package (`packages.spec_check`), with a matching flake check, development shell entry, and pre-commit hook.
2. Mechanical form rules checked by Lean on numbered specifications include character set, list markers, excess hyphenated tokens in prose (lowercase token with two or more hyphens), leftover unstack phrases listed in `0005_CATE.md`, a Residual heading when a numbered specification other than this document contains a planned or unpublished `NNNN_*.md` token, trailing whitespace, leading indentation that uses tabs only, detection of prose wrapped to a column, and related form rules, and MAY grow as the Lean checker covers more clauses.
3. Trailing whitespace and leading indentation that uses tabs only, on Surmount authored text files across the project (not only numbered specifications), SHALL be enforced by a pure Nix flake check (Nix language evaluation over the tree; see `nix/whitespace.nix` and `checks.whitespace`). That check is not bash and not Lean. It skips vendor blobs under `ref/` such as the SemVer submodule, PDFs, and RFC plain text, and applies the Lean/YAML indent exceptions in Clause 6.5.
4. Dual whitespace coverage is intentional and both checks SHALL remain: Lean enforces trailing whitespace and leading indentation that uses tabs only on numbered specifications as part of the form suite (item 2); pure Nix enforces the same class of rules across the tree on Surmount authored text (item 3). Neither layer replaces the other. Design rationale for that split (and for keeping spelling and form policy that takes more than one pass in Lean rather than pure Nix) is informative prose in `README.md` section 7.2.1 and in `AGENTS.md` under "Why Lean vs pure Nix"; those documents are not additional normative checkers.
5. American English spelling against the repository personal word list SHALL be enforced by the Lean `spec_check` program, which invokes `aspell` from PATH (`list --lang=en_US --mode=markdown`) with `aspell_words.txt`. The flake check `checks.spec_check` supplies `pkgs.aspellWithDicts` on PATH so spelling runs in CI. Spelling is not a separate flake check, not a shell package, and MUST NOT rely on a repository `scripts/` gatekeeper or a bash discovery policy that spans multiple lines.
6. Documents in scope SHALL remain checkable by the relevant authoritative checker when it is available for a given clause.
7. Markdown path links in numbered specifications (Clause 11.4) SHALL be checked by a Lean program packaged through the repository Nix flake (`packages.repo_links_check` and `checks.repo_links_check`). That program is not a second form suite for ASCII, spelling, or leftover unstack. It does not parse every HTML `href`.
8. `README.md` SHALL contain a table, always kept current, that states whether any proven logical inconsistency exists in this repository's Lean meaning models, and if so the file and the claim.
