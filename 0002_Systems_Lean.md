## 1. Scope

This document specifies Systems Lean, the language and compiler substrate required by Surmount high assurance components, including the Surmount Systems Smart Symbolic Supercompiler specified in [0004_SSSSS.md](0004_SSSSS.md). The aim of those components is performance, correctness, security, safety, reliability, high assurance, and as much systems parallelism as one client can use. One client means one client, not ten thousand concurrent clients, and not ten million concurrent clients. Meeting that aim is not claimed.

Systems Lean is Lean 4 extended with linear and affine ownership and the minimum Quantitative Type Theory (QTT) multiplicities needed for freestanding systems programming. Its freestanding compiler product is named Slake.

This document is the contract that humans read. It does not contain Lean theorem statements. Selected checkable claims have a companion Lean model under `lean/` (see Clause 1.2). That model is not this specification.

## 3. Definitions

### 3.1 Systems Lean

Lean 4 with linear and affine ownership and Quantitative Type Theory multiplicities restricted to 0, 1, and omega as defined in this clause.

### 3.2 Slake

The compiler written in Systems Lean that emits freestanding products.

### 3.3 Freestanding product wire

The binary or C source emitted by Slake that contains no managed Lean runtime and performs no garbage collection.

### 3.4 Multiplicity 0

Erased at compile time. A multiplicity 0 quantity MUST NOT appear in the freestanding product.

### 3.5 Multiplicity 1

Linear or affine use: exactly once or at most once.

### 3.6 Multiplicity omega

Unrestricted use. In this ASCII document the name is the word omega, not a Greek letter.

### 3.7 Residual

A named, tracked fact that prevents a product from being fully freestanding. Residual honesty means such a fact is explicit. Silence about a remaining managed runtime, garbage collector, or other blocker is nonconforming. Residual honesty does not replace CompCert verified compilation (Clause 4.2 item 6) or a bootstrapped Slake that fully typechecks (Clause 4.2 item 7). Silence is not a `FastC` mark, a `SafeC` mark, or a `FastSafeC` mark.

### 3.8 Requirement keywords

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY, and OPTIONAL in this document are to be interpreted as described in RFC 2119.

### 3.9 CompCert verified compilation

CompCert verified compilation is compilation by CompCert (`ccomp`) such that the generated assembly is the CompCert verified compilation of that C. `ccomp` is one metric. It is optional. It is not the only metric. It is not a speed claim and it is not comparison language. It is not claimed done. `SafeC` may include CompCert (`ccomp`). When `SafeC` is not combined with `FastC`, that inclusion is optional. `SafeC` can include `ccomp`, and `SafeC` is not required to include `ccomp`. `FastSafeC` is the overlap of `SafeC` and `FastC`. For `FastSafeC`, `ccomp` is also optional. `FastSafeC` can include `ccomp`, and `FastSafeC` is not required to include `ccomp`. An unmarked freestanding C emit is not required to be compiled with `ccomp`. A freestanding C emit marked `FastC` that is not combined with `SafeC` is performance priority and is not security priority. Optional does not mean forbidden: a program may still be compiled with `ccomp`. Silence does not select `FastC`, `SafeC`, or `FastSafeC`.

### 3.10 Slake that fully typechecks

A bootstrapped Slake compiler that typechecks the Systems Lean and Slake sources it is bootstrapped from, including theorems. The typecheck MUST cover all Slake code, including theorems. `FastC` is not an exception. Security priority is not an exception. There is no exception that removes Slake code from that typecheck. Developers and agents MUST always run that typecheck. A user who is building finished code MAY skip running that step. The skip is about who runs the check. It does not exempt the Slake code, and it does not make the bootstrap typecheck done. A `FastC` mark does not make that typecheck done, and it does not waive the typecheck of Slake code. A named subset of modules is not enough. Emitting freestanding C without that typecheck is not enough.


### 3.11 `SafeMem`

`SafeMem` means all of the following hold:

1. There is no use after free and no double free.
2. There is no access out of bounds.
3. There is no read of owned storage that has not been initialized.
4. There is no free while another owner of that block remains in that process.
5. There is no loan that outlives its owner or its frame, including an interior loan of a field or a slice on that block.
6. There is no `CopyHandle` of an `OwnerHandle` unless an alias protocol allows it (Clause 3.27).
7. There is no write into an `ObjectCow` object or a `PageCow` object while that object is not unique (Clause 3.39 and Clause 3.40).

`SafeMem` does not imply `PanicFree` (Clause 3.23).

### 3.12 `SafeThr`

`SafeThr` means there is no data race on a location that is not atomic, and atomic operations follow the order the program writes. A data race is two threads, one location that is not atomic, at least one write, and no happens before edge.

### 3.13 `SafeLayout`

`SafeLayout` means layout compatibility (`LayoutCompat`) holds for the program. Where a Fargo gate applies, virtual table compatibility (`VTableCompat`) and binary interface compatibility (`AbiCompat`) are further conjuncts. A claim of LLVM fragment compatibility (`IrFragCompat`) is not claimed proved in this clause (Clause 6.4).

### 3.14 `KernelModelOk`

`KernelModelOk` means the kernel model accepts the program. It is a conjunct of `SafeKernel`. It is not CompCert refinement. It is not a proof of mainline Linux.

### 3.15 `SafeKernel`

`SafeKernel` of a program means `SafeMem`, `SafeThr`, `SafeLayout`, and `KernelModelOk` all hold for that program. This judgment is not named `SafeLinux`. This document does not claim that mainline Linux is proved.

### 3.16 `CompCertFragment`

`CompCertFragment` is the fragment of C that excludes a listed set of undefined behavior. It is the fragment CompCert (`ccomp`) compiles when `SafeCompCert` holds. The first fragment is sequential unique C. Official CompCert does not prove threads. The constructor `container_of` is outside this fragment (Clause 3.34). An inline assembly island is outside this fragment. Treating full ISO C as an isomorphism is not a completion condition. Clashes named in Clause 5 and Clause 6.4 are fixtures. A clash that is not yet named is recorded when it is found and is not dropped (Clause 6.4).

### 3.17 `CompCertRefines`

`CompCertRefines` means the generated assembly is the CompCert refinement of that sequential unique C. It ties Clause 3.9 to `CompCertFragment`. It is not claimed done (Clause 6.3). Inhabiting the constructor `holds` is not a claim that a real emit was refined.

### 3.18 `SafeCompCert`

`SafeCompCert` of a program means `SafeKernel` of that program, `CompCertFragment`, and `CompCertRefines` all hold. `SafeCompCert` implies `SafeKernel`. The converse is False (Clause 4.5 and Clause 5). `SafeKernel` is not by itself `SafeCompCert`. `SafeC` is the family of Safe judgments already named, composed of `SafeMem`, `SafeThr`, `SafeLayout`, `SafeKernel`, and `SafeCompCert`. `SafeC` may include CompCert (`ccomp`). When `SafeC` is not combined with `FastC`, that inclusion is optional. `SafeC` can include `ccomp`, and `SafeC` is not required to include `ccomp`. `SafeC` can be combined with `FastC`. That combination is `FastSafeC`. `FastSafeC` is the overlap of `SafeC` and `FastC`. The `FastSafeC` balance rule is that overlap together with the named metrics. The named metrics are the Safe judgments, the `FastC` proofs of parallelism, `atomics`, threading, and proved freedom from locks, the Slake typecheck, and byte identity of emit. CompCert (`ccomp`) is optional and is one metric. It is not the only metric. The overlap is required to prove the best balance between safety and performance. The proof of that balance has not been carried out. That proof is not claimed finished. The rule is not an open question. For `FastSafeC`, `ccomp` is also optional. `FastSafeC` can include `ccomp`, and `FastSafeC` is not required to include `ccomp`. `ccomp` is one metric of that overlap and is not the only metric. This document does not invent `FastSafeC` block syntax. Further `SafeC` level names besides `FastSafeC` are not specified yet (Clause 6.4). `FastC` is the judgment that a freestanding C emit is performance priority. It is not security priority. `FastC` is not `SafeCompCert`. `FastC` composes with `SafeC`. A program may contain both. `FastC` is proved for the concurrency claims already named for parallelism, `atomics`, threading, and `LockFree` (Clause 3.37, Clause 3.48, and Clause 4.5 item 12). Where `LockFree` holds, those claims are proved free of locks. A Rust `unsafe` block is only an analogy for an explicit mark. This document does not claim Rust semantics. `FastC` that is not combined with `SafeC` is not required to use CompCert (`ccomp`). Optional does not mean forbidden. Block syntax for `FastC` is not specified (Clause 6.4). `FastSafeC` does not replace `SafeC` and does not replace `FastC`.

### 3.19 Reject

Reject means the `typer` refuses the program before emit. Reject is what a product shows. Reject is not a Fault. A reachable panic is Reject.

### 3.20 Fault

Fault means an illegal state of Step. Fault belongs to the specification of execution. The emitted binary is not a sanitizer that discovers Fault at run time in place of Reject.

### 3.21 Step

Step is the operational semantics. Reaching a Fault is a statement about Step. Step is not the emitted ELF.

### 3.22 `TyperSound`

`TyperSound` is the named implication that if the `typer` accepts a program, execution under Step does not reach a Fault. The `typer` matches Step as Clause 3.21 defines Step. `iris-lean` is not required and is not a dependency. The name is required. The companion fragment implication on `TyperFragment` is proved in the Systems Lean proofs module. The product `typer` is not done. Full product `TyperSound` still lags (Clause 6.4). Systems Lean remains not ready for use.

### 3.23 `PanicFree`

`PanicFree` of a program means a typed path has no reachable panic, unwrap, expect, failing assertion, typed access out of bounds, overflow that panics, or abort. `PanicFree` does not mean allocation never fails. `PanicFree` does not mean a hardware fault never happens. `SafeMem` does not imply `PanicFree`. `PanicFree` is a separate conjunct from `TyperSound`.

### 3.24 `PanicFreeAOT`

`PanicFreeAOT` is the named implication that if `PanicFree` holds of a program, execution does not reach a panic. The name is required. The companion fragment implication on `PanicFreeFragment` is proved in the Systems Lean proofs module. The product `AOT` path is not done. Full product `PanicFreeAOT` still lags (Clause 6.4). `PanicFreeAOT` is not `TyperSound`. Systems Lean remains not ready for use.

### 3.25 Bits

Bits are values with no identity and no `destructor`. `CopyBits` of Bits does not create an owner. A natural number, a Boolean, a numeric machine word, and a structure whose fields are only Bits are Bits. A handle is not Bits. An address word is Bits that name a block, and copying that word creates a second name. An `untyped` address word copy is that second name. It is not `CopyBits` of an `OwnerHandle`. A handle is an address word typed as an `OwnerHandle` or a `LoanHandle`. That typed handle is not copied as Bits.

### 3.26 `UniqueBlock`

`UniqueBlock` is a judgment of one process identifier and one block. The process identifier is an argument of the judgment. It is not a header field and it is not a reference count. `UniqueBlock` means the owner set of that block in that process has size one. Loans MAY still exist. A loan is not an owner. `UniqueBlock` says nothing about any other process. A `UniqueBlock` has no default reference count header (Clause 4.5). An `OwnerHandle` is a handle typed as an owner. A `LoanHandle` is a handle typed as a loan. Neither handle is Bits (Clause 3.25). A block is `UniqueBlock` in a process only when every page of that object is unique in that process.

Sharing that a crate already records in a header is that crate alias protocol, obtained by correspondence. It is not the default `malloc` path. This document does not invent a ghost owner count as a substitute for that header. An exact owner count on a header type is a later tool and is not claimed here (Clause 6.4).

### 3.27 Alias protocol

An alias protocol is how a heap block whose owner set in a process has size at least two is allowed to die. The constructors named for that protocol are a crate header that already counts references (`Arc` or `Rc` as that crate defines them), `MutexOwns`, and `JoinBeforeFree`. The default protocol is none. The default block is `UniqueBlock` only. `CopyHandle` of an `OwnerHandle` with no alias protocol is Reject, and that clash is False (Clause 4.5 item 3). A reference count field is allowed only as the counted protocol named `Protocol.Counted`. Tracing garbage collection on product clean emit is not a goal (Clause 6.4).

### 3.28 Passing modes

The five passing modes are `CopyBits`, `MoveOwner`, `LoanShared`, `LoanMut`, and `CopyHandle`. No other passing mode is permitted (Clause 4.5).

1. `CopyBits` copies Bits and does not create an owner.
2. `MoveOwner` transfers the owner and the source does not remain an owner.
3. `LoanShared` is a shared loan and does not free the block. Shared loans of ranges MAY overlap.
4. `LoanMut` is an exclusive loan and does not free the block. A `LoanMut` of a whole object conflicts with any loan of a field of that object. Exclusive loans of ranges are disjoint.
5. `CopyHandle` copies an owning handle and creates an extra owner. Without an alias protocol that extra owner is Reject (Clause 3.27).

Framing is the passing mode on each pointer or file descriptor in a function type: move, loan, or `CopyHandle`. A missing framing mode is the named stash. It is not a sixth passing mode. If the `callee` type does not state one of those modes, the `callee` MAY stash the pointer. `UniqueBlock` does not survive that stash. `UniqueBlock` is false after that stash. Two reads of a unique pointer are not an owner set of size two. A loan of a field is a range loan on the same block, not a new block. A free while any interior loan on that block is live is Reject.

### 3.29 Multiplicities, grades, and omega as an owner

Systems Lean keeps Quantitative Type Theory multiplicities 0, 1, and omega as defined in Clause 3.4, Clause 3.5, and Clause 3.6. No other multiplicity is permitted (Clause 4.1 item 1). Grade names used with the Safe judgments map onto those multiplicities and onto passing modes as follows.

1. Erased means gone at run time and matches multiplicity 0. An erased quantity does not appear in the freestanding product (Clause 3.4).
2. Once means consumed once, local to the function, and matches a multiplicity 1 use. Grade Once is not lock Once. Grade Once does not imply `UniqueBlock`.
3. Trivial means `CopyBits` of Bits only (Clause 3.25 and Clause 3.28). Trivial is the only Safe case of many uses that resemble omega.
4. Heap use of omega as an owner is Reject. That Reject is not the Trivial case. The two claims are not the same claim. Language level omega, when a text mentions it, applies only to Bits. It does not apply to a heap `OwnerHandle` (Clause 4.5).

In this ASCII document the multiplicity name remains the word omega, not a Greek letter (Clause 3.6).

### 3.30 Profiles

1. `HostedLinuxLibc` means ISO hosted emit that is product clean (Clause 3.31), with `libc` and Linux in the trusted computing base, and with an entry point named `main`. Sequential unique C on this profile aims at `SafeCompCert`. Threads and `atomics` on this profile are `SafeKernel` and are not by themselves `SafeCompCert`. This profile is additional. It is not the freestanding product wire (Clause 3.3). Clause 4.5 item 6 does not allow that profile to replace the wire. The v28 package names this profile as its default. This document keeps the profile additional. That package does not implement Linux, `glibc`, Wild Child, FixOS, or fit.
2. `LibcOnly` means the trusted computing base includes `libc` and the user syntax contains no raw system call.
3. `FargoLlvm` means elevation of a Rust crate through LLVM IR, with layout compatibility and Rust trait object tables. The name does not assign fargo a specification number (Clause 3.47).
4. `FreestandingKernel` means ISO freestanding emit that is product clean, with no hosted `libc` in the trusted computing base, and with a kernel or firmware entry. It is not bare metal by itself. It is not the Rust attribute `no_std`.

### 3.31 Words that are not synonyms

Hosted, ISO freestanding, product clean, bare metal, and the Rust attribute `no_std` are not synonyms.

1. Hosted means the program runs with an operating system and a C library, in the hosted form of C.
2. Freestanding means the freestanding form of ISO C. That word is a term of art and this document keeps it. The freestanding product wire (Clause 3.3) is product clean and is distinct from hosted emit. The freestanding form is the section numbered 5.1.2.1 of ISO/IEC 9899:2024. The pin file is absent because the license forbids it (Clause 6.4).
3. Product clean means the emit has no managed Lean runtime and no managed Idris runtime.
4. Bare metal means there is no operating system.
5. `no_std` is a Rust attribute. It is not ISO freestanding, it is not product clean, and it is not bare metal.

### 3.32 Correspondence

Correspondence is a map from judgments on a named fragment to Safe judgments, together with a map back. One map sends a Rust judgment to a Safe judgment or to no judgment. The other map sends a Safe judgment back. Both maps are partial until a gate says otherwise. An isomorphism on a fragment is the further claim that both maps are total on that fragment and compose to identity. Correspondence MUST be in place before any isomorphism claim. Until that theorem exists, text MUST say correspondence of judgments on the fragment and MUST NOT call the maps an isomorphism (Clause 4.5 item 9). Curry-Howard in this clause means a correspondence of rules. It does not mean a finished category isomorphism. A test of the maps is not that theorem.

A language behavior that the source language leaves undefined, leaves to the implementation, or gets silently wrong is Reject, a named Fault, or a named trusted island. Those maps are correspondence. They are not an isomorphism until the identity condition holds. Full ISO C and full ISO C++ as `isomorphisms` are not completion conditions (Clause 6.4).

### 3.33 Cons

Cons of a set of judgments means that set does not prove False from its own constructors and axioms. A clash of two constructors that cannot both hold is False in the companion Lean proofs, not a comment. A clash that would be a vulnerability is Reject or a failed Cons fixture. Cons does not mean every true statement has a proof. It means the claims this document writes do not contradict one another. The fixtures that are False are named in Clause 4.5 item 3 and Clause 5. A fixture that exists only as a test and does not record False does not meet that item.

### 3.34 container_of

The constructor `container_of` recovers a containing object from an interior field using a documented offset and an identifier of that containing object. It is a `SafeKernel` constructor. Silent recovery, with no documented offset and no identifier, is Reject on a `SafeCompCert` claim. `CompCertFragment` together with `container_of` is False (Clause 4.5 item 3). The containing object is an ordinary data object. The word is not an agent layer. `list_entry` is a `SafeKernel` constructor of the same class, with a parent identifier and a documented offset. Silent recovery on that constructor is Reject on a `SafeCompCert` claim.

### 3.35 Lock catalog

Phase 0 of the lock catalog is the following names plus a linear `LockToken` (Clause 3.36). Encoding the whole catalog as proved is not required and is not claimed done.

1. `Mutex` is an exclusive lock that owns its payload. Taking the lock yields a `LoanMut` of that payload paired with a `LockToken`. Releasing the lock consumes both and restores the `Mutex`. `Mutex` does not admit shared readers.
2. `RwLock` admits many `LoanShared` or one `LoanMut`, and not both at once. A write is permitted only when no reader token and no writer token remain.
3. Semaphore is a counter of linear permits. Waiting decrements the counter and returns a permit. Post consumes a permit or creates one when the initial bound allows it. A binary semaphore has maximum one. A counting semaphore has maximum N chosen at the start.
4. Permit is the linear token a Semaphore grants. A Permit is not an owner of a heap block.
5. `Condvar` is a wait queue attached to a `Mutex`. Waiting consumes a `LockToken` and later returns a new `LockToken`. The type does not by itself solve a missed wake up.
6. Barrier collects a fixed number of linear arrival tickets and then releases them. Using one ticket twice is Reject.
7. Once initializes a block exactly once. The first writer receives `LoanMut`. Later readers receive `LoanShared`. A second writer is Reject.
8. `AffineUnlock` means dropping the guard releases the lock. Forgetting a live `LockToken` is Reject unless a documented leak island applies. This name is not a finished proof.
9. A try of the lock (`trylock`) returns a result. It does not panic because the lock is busy.
10. A recursive `mutex` is named and is off unless a profile turns it on.
11. Lock poisoning is named. This clause does not claim a poisoning proof.
12. `SeqLock` is a named lock. The writer receives `LoanMut`. Readers take a snapshot and retry. A proof of `SeqLock` may lag and is not claimed done. `Futex` is an atomic on `ProcessShared` memory, or on a word the kernel owns, and that equation is not a proved theorem. `LockOrder` and `lockdep` come later and are not claimed. A ticket does not prove that deadlock is absent (Clause 3.36 and Clause 6.4).

What a linear `LockToken` changes is that the token cannot be copied, that `Mutex` owns the payload, that `RwLock` is many shared loans or one exclusive loan, and that an `ObjectCow` or `PageCow` write that does not copy when the object is shared is Reject. What it does not provide is absence of deadlock, absence of `livelock`, fairness, or a correct scheduler. What Systems Lean adds, beyond a `mutex` and `atomics` that Rust and C++ already have, is one proposition the kernel model checks and that Fargo can require. That proposition is the linear `LockToken`, the Reject of a copy on write that writes the shared object without copying, the Reject of Secret key material on an `Arc` unless a protocol says those bytes are not secret, and a `UniqueBlock` with no default reference count header.

### 3.36 `LockToken`

`LockToken` is a linear proof that this thread holds one identified lock. The grade is Once (Clause 3.29). `CopyHandle` of a `LockToken` is Reject. Unlock consumes the `LockToken`. A second unlock is Reject. A missing unlock of a live `LockToken` is Reject. `LockToken` does not prove that deadlock is absent (Clause 4.5).

### 3.37 `LockFree`

`LockFree` is the claim that an implementation matches a sequential specification under a named sharing mode, that an operation does not leave an inconsistent state, and that the operation does not block other parties that mode allows. `LockFree` is not the absence of a `Mutex`. `LockFree` is not compare and swap. `LockFree` is not an atomic transaction and it is not the four transaction words in Clause 3.38. The progress claim is that sentence. It is not wait free and it is not obstruction free (Clause 3.55). Proofs of that claim are not claimed done (Clause 6.4). A structure that frees a node and calls itself `LockFree` with no named reclamation protocol is not accepted as `LockFree` (Clause 6.4).

### 3.38 ACID words and specification [0003](0003_beastdb.md)

Atomicity, consistency, isolation, and durability are four words for a transaction. They are not compare and swap. They are not a hardware atomic. They are not a `Mutex`. They are not `LockFree`. Isolation takes a named level. This document does not choose that level for beastdb. Specification [0003_beastdb.md](0003_beastdb.md) Clause 3.6 owns proved ACID for beastdb. Clause 3.7 of that specification owns tries that do not use locks. This document does not move those theorems here and does not restate them as theorems of Systems Lean (Clause 4.5). The stack row for beastdb relies on mapped memory and `ZeroView` when those proofs exist. That reliance is not a theorem of this document. The single writer, multiple reader default of beastdb stays in that specification. v28 requires that mode for beastdb, and it allows many writers and many readers on leaves that do not overlap. `AtomicTxn` and durability attach when those proofs exist. Those store rules stay in specification 0003.

### 3.39 `ObjectCow`

`ObjectCow` is a heap object protocol. A share does not copy bytes. A write when the owner set has size greater than one copies the payload to a new `UniqueBlock`. A write into the shared object while it is not unique is Reject. `ObjectCow` is the protocol that matches a mutating copy of a shared heap object. It is not `PageCow`. It is not `BorrowOrOwned`. It is not `PosixFork` (Clause 3.42). The name `make_mut` denotes `ObjectCow`.

### 3.40 `PageCow`

`PageCow` is a page table protocol. A shared physical page is protected against writes, and the first store copies that page. The copy is one 4096 byte page. That page is the ordinary 4KB page, and it lines up with a 4KB sector. A larger hardware page is allowed when it improves performance for that one client. That larger hardware page is not a second copy. The copy stays one 4096 byte page (Clause 6.4). `PosixFork` on a private mapping is `PageCow` (Clause 3.42). A write into a `PageCow` page while it is not unique is Reject.

### 3.41 `BorrowOrOwned`

`BorrowOrOwned` is either a loan or an owned copy. It is the Fargo name for the Rust standard library `enum` that holds one of those two. `BorrowOrOwned` is not `ObjectCow`. `BorrowOrOwned` is not `PageCow`. `PosixFork` is not `BorrowOrOwned`.

### 3.42 `PosixFork`

`PosixFork` is the POSIX fork operation that creates another process. `ForkJoin` joins threads inside one process. `PosixFork` is not `ForkJoin`. `PosixFork` is not `ObjectCow` and is not `BorrowOrOwned`. On a private mapping, and on anonymous heap pages, `PosixFork` is `PageCow`. File descriptors are duplicated and are not `PageCow`. A mapping that stays shared across the two processes stays shared. A program whose blocks are unique only rejects `PosixFork` (Clause 4.5). `PosixFork` while a Secret with `DontFork` is live is Reject (Clause 3.43 and Clause 3.44). A pin of an address does not survive `PosixFork`. Message passing of an owner uses `MoveOwner`, and message passing of bits uses `CopyBits`. Both travel across threads through a channel. That channel is `ForkJoin` traffic, not `PosixFork` (Clause 6.4).

### 3.43 Secret

Secret means the bytes are not copied by `CopyHandle` or by `CopyBits` into a sink that is not Secret. `ObjectCow` of a Secret is Reject. `PageCow` of a Secret is Reject. Those two clashes are False (Clause 4.5 item 3). `DontFork` is the default while a Secret block is live (Clause 3.44). `WipeOnConsume` applies to Secret (Clause 3.45). A reference counted crate pointer whose payload is key material is Reject unless an explicit protocol says those bytes are not secret. That includes an `Arc` of key material. Keys are an `OwnerHandle` or a pinned `UniqueBlock`. The v28 flagship line also names that pin optional. This document keeps the pin when the key is a `UniqueBlock`, and an `OwnerHandle` key may omit the pin.

### 3.44 `DontFork`

`DontFork` means `PosixFork` is Reject while this block is live in the forking process.

### 3.45 `WipeOnConsume`

`WipeOnConsume` means the payload bytes are set to zero before the owner dies. A Secret MUST use `WipeOnConsume` (Clause 4.5 item 11).

### 3.46 `SafeCt`

`SafeCt` means control flow and data access do not depend on Secret. `SafeCt` is off by default. A profile that wants `SafeCt` says so. Silence leaves `SafeCt` off and does not turn `SafeCt` on (Clause 4.5). When a profile turns `SafeCt` on, timing, cache behavior, and page faults do not depend on Secret and do not carry Secret (Clause 6.4). Failure to be constant time is not that switch.

### 3.47 Fargo gates A through F

Fargo is the `SurmountSystems` cargo fork named fargo. This document does not assign fargo a specification number (Clause 6.2 item 2 and Clause 6.4). Gates A through F are obligations a correspondence MUST prove (Clause 3.32). They are not a specification number and they are not a numbered file.

1. Gate A. The syntax fragment contains no `unsafe` code, or `unsafe` code is isolated behind an `OwnerHandle` interface the Safe judgments can see.
2. Gate B. Every type from the Rust compiler (`rustc`) maps to Bits, an `OwnerHandle`, a `LoanHandle`, or Reject.
3. Gate C. Each function passing mode maps to one of the five passing modes in Clause 3.28.
4. Gate D. Layout compatibility holds for every type that crosses a binary interface or is stored in a structure Fargo emits.
5. Gate E. Virtual table compatibility holds for every trait object Fargo emits.
6. Gate F. Product clean emit, as C or as LLVM IR, contains no managed Lean runtime and no managed Idris runtime.

A crate that meets Gate A and does not meet Gate D, Gate E, and Gate F is not Safe (Clause 4.5 item 9). This clause does not make Fargo run cargo. This document states what a gate MUST prove. Elevation of these gates in the fargo fork is not claimed implemented (Clause 6.4).

### 3.48 Emit split

The emit split is which compiler runs. CompCert (`ccomp`) applies when `SafeCompCert` holds, on sequential unique C. LLVM or `cc` applies when only `SafeKernel` holds, including `atomics`, device registers, explicit packed vector operations, and assembly islands. The LLVM or `cc` path is not proved by CompCert. CompCert does not prove layout compatibility against `rustc`. That layout obligation is the LLVM and Fargo path. The primary emission target of Slake stays freestanding, runtimeless C (Clause 4.2 item 2). `HostedLinuxLibc` is an additional profile (Clause 3.30). It is not a silent replacement of that primary target. CompCert (`ccomp`) is one metric. It is optional. It is not the only metric. When `SafeC` is not combined with `FastC`, inclusion of CompCert (`ccomp`) is optional. `SafeC` can include `ccomp`, and `SafeC` is not required to include `ccomp`. `FastSafeC` is the overlap of `SafeC` and `FastC`. For `FastSafeC`, `ccomp` is also optional. `FastSafeC` can include `ccomp`, and `FastSafeC` is not required to include `ccomp`. `ccomp` is one metric of that overlap and is not the only metric. The other metrics are the Safe judgments, the `FastC` proofs of parallelism, `atomics`, threading, and proved freedom from locks, the Slake typecheck, and byte identity of emit. The `FastSafeC` balance rule is that overlap together with those named metrics. The overlap is still required to prove the best balance between safety and performance. The proof of that balance has not been carried out. That proof is not claimed finished. The rule is not an open question. An unmarked freestanding C emit is not required to be compiled with `ccomp`. Security priority does not always require `ccomp`. Optional does not mean forbidden: a program may still be compiled with `ccomp`. `ccomp` being an optional metric does not make CompCert verified compilation done. A freestanding C emit marked `FastC` that is not combined with `SafeC` is performance priority and is not security priority. Silence does not select `FastC`, `SafeC`, or `FastSafeC`. `FastC` points at the parallelism, `atomics`, threading, and `LockFree` clauses already named in this document. It does not state a new memory model.

### 3.49 `LinkFace`

`LinkFace` is the exported ownership of a typed object or archive: symbol names, layouts, and the passing modes `MoveOwner`, `LoanShared`, `LoanMut`, `CopyHandle`, and Bits. A classic linker concatenates sections and resolves symbols. It does not check that a relocation is a loan. Until Wild Child exists, `cc`, `ld`, `lld`, and the upstream Wild linker stay in the trusted computing base and do not preserve `UniqueBlock` (Clause 6.4). A symbol clash, a layout mismatch, or a `UniqueBlock` exported as Bits is Reject. That last clash is False (Clause 4.5 item 3). The typed link output is one ELF file or one shared object whose combined program is `SafeKernel`, or `SafeCompCert` when every linked unit is `CompCertFragment`. A typed library may stay Safe for typed callers. The process that calls `untyped` code is not Safe.

### 3.50 `ThreadShared` and `ProcessShared`

`ThreadShared` means a block is reachable from two threads in one process. It is not a map. `ProcessShared` means two virtual mappings name one physical page under a shared map. `ThreadShared` is not `ProcessShared`. Treating those two words as one word is False (Clause 4.5 item 16).

### 3.51 `AtomicCell` and compare and swap

`AtomicCell` is a location that MUST be touched only with atomic operations. `HwAtomic` is a hardware atomic. Compare and swap is a technique. The technique includes compare and exchange, weak compare and exchange, load linked with store conditional, and a double width compare and swap when the hardware has it. It is not `AtomicCell`. It is not `LockFree`. It is not an atomic transaction. Compare and swap on a plain `UniqueBlock` pointer is Reject. Compare and swap on a cell that is not `AtomicCell` is Reject. Those two clashes are False (Clause 4.5 item 3). `AtomicCell` and `AtomicTxn` remain unfinished product theories (Clause 6.4).

### 3.52 Correspondence maps

Correspondence maps are statements, not an isomorphism theorem. The named maps are `Corresponds`, `toSafeC`, and `toRust`. One direction sends a Rust judgment to a Safe judgment or to no judgment. The other sends a Safe judgment back. Both maps stay partial until a gate says they are total on a named fragment and compose to identity (Clause 3.32). This document MUST NOT name a theorem `Isomorphism`. Naming a theorem `Isomorphism` is False (Clause 4.5 item 3).

### 3.53 `UbClass`

`UbClass` is a named class of language behavior that the source language leaves undefined, leaves to the implementation, or gets silently wrong. Correspondence for each named class is a map from that class to an optional Fault and a map from a source construct to an optional class. An isomorphism on a fragment is allowed only when those maps are total on that fragment and compose to identity. Listing some classes is not that theorem.

Named C classes include signed integer overflow, an uninitialized read of automatic storage, use after free, double free, pointer arithmetic or an array subscript out of bounds, a data race, strict aliasing, a `restrict` violation, an invalid free, an `unsequenced` side effect, a shift exponent out of range, following a null pointer, pointer provenance misuse, a variable length array or a GNU statement expression or an empty GNU structure as Reject on `CompCertFragment`, overlapping `memcpy` ranges, and use of the old pointer after `realloc`. Named C++ classes include iterator invalidation after mutation, a reference bound to an expired temporary, `this` after lifetime ends, signed overflow, placement new lifetime, a `destructor` during unwind, a data race on a shared pointer control block, and mutation of a `const` object through `const_cast`. Named Rust classes include `unsafe` that manufactures aliasing exclusive loans, uninitialized storage without `MaybeUninit`, integer overflow as a named operation that `PanicFree` cares about, and `forget` of a live lock guard. Each named class in this clause is Reject before emit or is Fault under Step. That includes effective type beside strict aliasing, a pointer one past the end, C++ narrowing, and a data race on a shared pointer control block unless that block is used atomically. A `destructor` during unwind does not apply when that behavior is specified. Fargo does not elevate raw C++. A class that CompCert does not model stays `SafeKernel` only, and the island is named. An invalid free includes a pointer that did not come from `malloc` and a wrong size story. The Rust integer overflow split is a debug panic versus wrapping. A C++ fragment gets a correspondence row only when a crate or an emit path needs that fragment. A class that CompCert already excludes is Reject before `ccomp`. Calling C Safe while that C has signed overflow is a Cons clash. The product Fault table is not claimed complete (Clause 6.4).

### 3.54 `ZeroView` and `Pinned`

`ZeroView` means the layout of a type in memory is exactly the buffer bytes. Access is a shared loan of that view. `CopyBits` of the payload is Reject. `Unmap` while the view is live is Reject. `ValidView` adds alignment, bounds, an optional endian (`Le`, `Be`, or `Native`), a schema or generation tag, and an optional checksum. A relative pointer inside an archive is `RelPtr`. An implementation of the view is not claimed done (Clause 6.4). `Pinned` means the address MUST NOT move. `Pinned` is not immortal. A pin of an address does not survive `PosixFork`. Treating a pin as surviving `PosixFork` is False (Clause 4.5 item 3). The address stays pinned while a `ZeroView` lives. Unpinning a pinned address is documented. The reasons include a value that points at itself, `DMA`, device registers, `mlock`, and `ZeroView`.

### 3.55 Wait free and obstruction free

Wait free means an operation finishes in a bounded number of its own steps. Obstruction free means an operation finishes if it runs alone. Those two claims are not `LockFree`. The three progress claims are these definitions together with Clause 3.37. Proofs of them are not claimed done (Clause 6.4).

### 3.56 `UsesLock` and `LockHandled`

`UsesLock` means a path waits for exclusion. `LockHandled` means every such path releases a ticket or a guard and has a documented try, timeout, or spin policy. Those identifiers are named. Treating them as present theories is False (Clause 6.4 items 42 and 46). Clients should not observe a leaked or unbounded exclusion.

### 3.57 Reject fixtures

Reject fixtures are product facing. The `typer` MUST refuse each of the following before emit (Clause 3.19). A comment is not enough.

1. `CopyHandle` of an `OwnerHandle`, a `LockToken`, a Permit, or a Secret.
2. Trivial grade on a Handle.
3. Erased used at runtime.
4. Once used twice in one body.
5. Free while the owner set in that process has size at least two.
6. Free while an interior loan is live.
7. `ObjectCow` write in place while the owner set has size greater than one.
8. `PageCow` write in place while the mapper set has size greater than one.
9. `PosixFork` in a program whose blocks are unique only.
10. `PosixFork` while a Secret with `DontFork` is live.
11. `MoveOwner` of pinned device registers.
12. A data race on a `ThreadShared` location that is not atomic.
13. A reference count header on `UniqueBlock` without a shared owner protocol.
14. Load with Release or store with Acquire.
15. Compare and swap on a cell that is not `AtomicCell`.
16. `Unmap` or close while a loan or a `ZeroView` is live.
17. `UniqueBlock` exported on a `LinkFace` as Bits.
18. Stash of a loan into a global.
19. Forget of a live `LockToken` unless a documented leak island applies.
20. A reachable unwrap or typed access out of bounds on a `PanicFree` claim.
21. Unlock of a `Mutex` without a `LockToken`.
22. A second `RwLock` write while a read token lives.
23. `CopyHandle` of a key typed `OwnerHandle` in a cryptography fixture.

Pass fixtures that a later product MAY accept are named in Clause 6.4. They are not claimed green in this specifications repository.
