> v0.1.0 - 20260831

## 1. Scope

This document specifies Concise American Technical English (CATE) for numbered specifications in this repository and for agents that encode or revise those specifications. CATE is Concise American Technical English, and British spelling is nonconforming, including names we choose. The American form of the example is `catalog`. If you must show the British form, keep it in inline code.

This specification is number 0005. The file name is `0005_CATE.md`.

CATE is not specification 0006. Number 0006 is Recursive Self Improvement (`0006_RSI.md`). CATE is not an extension clause of `0000_spec.md`. Form rules remain `0000_spec.md`. Authors SHALL follow this specification when writing numbered specifications in this repository.

This document also specifies the evolving catalog of domain words that numbered specifications in this repository share. It is the map of domain words the spelling list allows, the `L_n` headings the checker parses, the isomorphism with `aspell_words.txt`, and the rule that other numbered specifications SHALL use these tokens as defined here when they use those words.

This specification evolves. Adding a token means an `aspell_words.txt` line, a heading the checker parses, a definition, and id renumber for that letter. The Lean isomorphism with the spelling list MUST stay green.

## 3. Definitions

### 3.1 CATE

Concise American Technical English as specified by this document.

### 3.2 Complete thought

A sentence or question that states a full idea in ordinary American English. A half label used as if it were a sentence is not a complete thought.

### 3.3 Half label

A fragment that names a topic without stating a complete American English thought (for example a short caption used as if it were a question to a human).

### 3.4 Leftover unstack

The result of deleting a hyphen from a compound of the kind used in legal captions and leaving the same two words. Leftover unstack is nonconforming. Rephrasing into ordinary English is conforming.

### 3.5 Leftover unstack floor list

The phrases Lean `spec_check` flags in numbered specification prose outside fenced code and outside inline code. The same list and scan apply to compiled Lean spec encodings: sibling encoding `encodedLines` outside fenced code and outside inline code, and comments in the fourteen paths `lean/FormalVibeficationSpec.lean`, `lean/VocabularySpec.lean`, `lean/Vocabulary.lean`, `lean/TechTreeSpec.lean`, `lean/MemexSpec.lean`, `lean/UnlicenseSpec.lean`, `lean/CateSpec.lean`, `lean/RsiSpec.lean`, `lean/CiSpec.lean`, `lean/BeastDbSpec.lean`, `lean/SssssSpec.lean`, `lean/SystemsLeanSpec.lean`, `lean/LeanMachineSpec.lean`, and `lean/AnunnakiSpec.lean`. The list is a floor, not a complete English checker. Authors still SHALL rephrase other leftover pairs the checker does not name. The current floor list is:

```text
non markdown
must like
LF only
lock free tries
fully type checking
copy grain
first grain
page grain
```

Writers MUST NOT coin `copy grain`, `first grain`, or `page grain` for a `PageCow` copy. `PageCow` copies one 4096 byte page. That page is the ordinary 4KB page and it lines up with a 4KB sector. A larger hardware page is allowed when it improves performance for the one client. The copy stays one 4096 byte page. It is not a second copy size.

### 3.6 Residual record

A record on disk that names unpublished specifications, unassigned numbers, unpinned prior art, unimplemented requirements, and out of scope items the document names. A parenthetical planned file name in Scope is not a residual record. Silence about residual is nonconforming when those items are named.

### 3.7 Encode effort

The work of writing or revising a numbered specification in this repository, including form, Lean meaning model, registry, residual, README, and the Nix flake check.

### 3.8 Independent work streams

Two or more encode jobs that do not share a write set. They SHALL run as parallel subagents. Serializing them without a shared write set is nonconforming.

### 3.9 Requirement keywords

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY, and OPTIONAL in this document are to be interpreted as described in RFC 2119.

### 3.10 Decoder ring jargon

Private labels that force the reader to decode a nickname instead of naming the real file, clause, product, or outcome.

### 3.11 Vocabulary

The evolving catalog specified by this document: shared domain words, `L_n` headings the checker parses, definitions in human prose, and the isomorphism with the spelling list.

### 3.12 L_n id

An identifier of the form uppercase letter, underscore, and a positive decimal index that starts at 1 for that letter, written next to a wrapping mark around the aspell token. Letter ids restart at 1 for each letter. Ids for letter L are `L_1` through `L_k` with no gaps.

### 3.13 Aspell token

One word from `aspell_words.txt` after the `personal_ws-1.1 en N` header. The product name beastdb is always the seven lowercase letters. `Changelog` and `changelog` are two tokens and two ids.

### 3.14 Catalog

The letter headings and entry headings the checker parses in this file, with the human prose definition that follows each entry heading.

### 3.15 Pointer file

Root `VOCABULARY.md`. It SHALL remain a short pointer to this specification so old links still work. It is not the catalog.

### 3.16 Collision

The same English word used in more than one tree. Collision tags in `lean/Vocabulary.lean` keep those uses distinct so equating the wrong pair is a type error.

### 3.17 Isomorphism of tokens

The pair of inverse maps between `aspell_words.txt` tokens and `L_n` entries in this file. Words under a letter are sorted by ASCII without regard to case, then by ASCII code when the folded forms tie.

## 4. Core requirements

### 4.1 Complete American English thoughts

1. Authors SHALL write complete American English thoughts.
2. Authors SHALL NOT use half labels as sentences.
3. Complete sentence quality beyond the leftover unstack floor list and the Residual heading check is not fully mechanical. Authors still SHALL write complete American English thoughts. That floor does not prove that every Lean comment is a complete American English thought.

### 4.2 Questions to humans

1. A question to a human SHALL name the file or clause.
2. A question to a human SHALL quote the current wording.
3. A question to a human SHALL say why the choice matters.
4. A question to a human SHALL name the options.
5. A question to a human SHALL use ordinary English.
6. When a question introduces a new phrase, it SHALL define that phrase in the same sentence.
7. A question to a human SHALL say what we will do for each option.
8. A half label is not a complete question.

### 4.3 Concise prose

1. Prefer one idea per sentence when that stays clear.
2. Authors SHALL NOT use decoder ring jargon.
3. Authors SHALL name the real thing: the file, the clause, the product, the checker, or the outcome.

### 4.4 Hyphenation and leftover unstack

1. Hyphenated compounds of the kind used in legal captions SHALL be rephrased into ordinary English as in `0000_spec.md` Clause 7.
2. Authors SHALL NOT delete the hyphen and leave the same two words. That leftover unstack is nonconforming.
3. The Lean `spec_check` program SHALL flag the leftover unstack floor list (Clause 3.5) in numbered specification prose outside fenced code and outside inline code.
4. The leftover unstack checker SHALL NOT flag `high assurance`, `3 bit`, or `time series` merely for having a space. `high assurance` may stay when it already reads as English.
5. Authors still SHALL rephrase other leftover pairs the checker does not name.

### 4.5 Residual in full

1. Residual SHALL be written in full on disk when the document names unpublished specifications, unassigned numbers, unpinned prior art, unimplemented requirements, or out of scope items.
2. A parenthetical planned file name in Scope is not enough.
3. For numbered specifications other than `0000_spec.md` (0001 and later published numbers), if the file contains a `NNNN_descriptive.md` token whose registry row is unpublished or planned, the file SHALL include a markdown heading titled Residual (for example `## 6. Residual`).
4. `0000_spec.md` is exempt from that heading check because it is the form spec and may cite later specifications.
5. Silence about residual is nonconforming.

### 4.6 Spec markdown and Lean

1. Numbered markdown is the contract that humans read.
2. Lean is a separate model of selected clauses.
3. Meaning proofs SHALL NOT be treated as a second markdown form checker.

### 4.7 No invented conforming product

1. Authors SHALL NOT claim that a conforming product exists unless the repository operator has said that product exists.

### 4.8 RFC 2119 is not replaced

1. CATE SHALL NOT replace RFC 2119.
2. Requirement keywords remain as in `0000_spec.md` Clause 4 and RFC 2119.

### 4.9 Independent work streams as parallel subagents

1. Independent work streams SHALL run as parallel subagents.
2. Authors SHALL NOT serialize two jobs that do not share a write set.
3. When two specifications must land in one effort, spawn one subagent per specification on disjoint files, then one pass on shared files (registry, README, `AGENTS.md`, residual, flake).

### 4.10 Self improvement of the encode process

1. When friction appears in the same encode effort (hyphen leftovers, incomplete questions, README wording that does not match the registry), authors SHALL improve the encode process in that same effort.
2. Authors SHALL prove that improvement with a Lean check or a skill step, not a chat reminder.

### 4.11 Size reports and git status

1. When the operator asked for size, authors SHALL run `scc --exclude-dir ref,.git,result,lean/.lake,.direnv --exclude-ext pdf .` before and after, including the COCOMO block.
2. COCOMO is fun and is not a real cost or schedule. Authors SHALL NOT pass `--no-cocomo`.
3. When the operator asked for git status, authors SHALL run `git status --short`.
4. Authors SHALL NOT run `git add` or `git commit` unless the operator explicitly asked for that git work.
5. Git remains forbidden in this repository unless the operator explicitly asked for that git work.

### 4.12 This specification is the map

1. This file is the catalog of domain words the spelling list allows.
2. Other numbered specifications in this repository SHALL use these tokens as defined here when they use those words.
3. Authors SHALL NOT treat root `VOCABULARY.md` as the catalog.
4. Definitions after entry headings remain human prose for meaning beyond the isomorphism. The isomorphism does not prove that those definitions match every use in other specifications.

### 4.13 Headings the checker parses

1. The Lean checker MUST parse each entry heading with this regular expression. A wrapping mark is written as hex 60 so this file can show the pattern without a raw wrapping mark ending a fence.

````text
^### ([A-Z])_([0-9]+) \x60([^`]+)\x60$
````

2. That pattern is a heading with three hash marks, then a space, then an uppercase letter, an underscore, a positive decimal index, a space, a wrapping mark, the aspell token, and a closing wrapping mark, and nothing else on the line. An example that matches is the heading for entry A_1 whose token is ABI.
3. Entry headings live outside fenced code.
4. Letter section headings SHALL be exactly two hash marks, a space, and one uppercase letter, and nothing else on the line, for each letter that has entries.

### 4.14 Adding a token

1. This specification evolves.
2. Adding a word under letter L inserts it in that letter's sort and renumbers that letter so ids stay `L_1` through `L_k` with no gaps.
3. Authors SHALL add the token to `aspell_words.txt`, add the heading the checker parses, and add a definition in the same effort.
4. Authors SHALL keep the Lean isomorphism green.

### 4.15 Sort and uniqueness

1. Words under a letter SHALL be sorted by ASCII without regard to case, then by ASCII code when the folded forms tie.
2. Each token SHALL have exactly one `L_n` id.
3. Duplicate ids and duplicate words do not conform.

### 4.16 Collisions stay tagged

1. Systems Lean is the language. Slake is the compiler. The Lake package id `SystemsLean` is not a second language name. Those three SHALL NOT be mashed into one fact.
2. Remaining work written on disk is not the Systems Lean named freestanding blocker and is not a product claim that a freestanding release has no managed Lean leftover.
3. Multiplicity omega in Systems Lean prose is an ASCII word. The companion Lean constructor for that multiplicity is `unrestricted`. Those two SHALL NOT be mashed into one name.
4. Leftover unstack is specified by this document. RSI does not replace that repair.
5. Companion Lean collision tags in `lean/Vocabulary.lean` SHALL stay as those distinct types.

### 4.17 Lean encodings and proofs

1. The catalog SHALL also be encoded in Lean as declarations of what must be true (structures, inductive types, and propositions).
2. For the catalog the spec encoding module is `lean/VocabularySpec.lean`. That module SHALL mark itself as a spec encoding and SHALL NOT mark itself as a proof.
3. Proofs SHALL live in `lean/VocabularyProofs.lean`. That module SHALL import the spec encoding module.
4. `toAspell` and `ofAspell` SHALL be inverses on well formed lists, as proved in that proof module.
5. Runtime isomorphism SHALL read `0005_CATE.md` and `aspell_words.txt`.
6. Lean proofs SHALL NOT be treated as the specification.
7. Numbered markdown SHALL NOT be treated as a substitute for those encodings.
8. Mixing spec encoding declarations and their proofs in one mash that hides the split is nonconforming in this specifications repository as specified in `0008_Formal_Vibefication.md`.

### 4.18 Sibling line encodings

1. This file SHALL have a sibling Lean spec encoding `0005_CATE.lean` at this repository root whose physical lines match this markdown, as specified in `0008_Formal_Vibefication.md`.
2. Proofs of that encoding SHALL live in `lean/Proofs_0005.lean`.

## Headings the checker parses

The Lean checker MUST parse each entry heading with this regular expression. A wrapping mark is written as hex 60 so this file can show the pattern without a raw wrapping mark ending a fence.

````text
^### ([A-Z])_([0-9]+) \x60([^`]+)\x60$
````

That pattern is a heading with three hash marks, then a space, then an uppercase letter, an underscore, a positive decimal index, a space, a wrapping mark, the aspell token, and a closing wrapping mark, and nothing else on the line. An example that matches is the heading for entry A_1 whose token is ABI. Entry headings live outside fenced code. Adding a word under letter L inserts it in that sort and renumbers that letter.

SSSSS is the Surmount Systems Smart Symbolic Supercompiler, numbered specification `0004_SSSSS.md`. The five consecutive S letters are an informative cultural marker. This specification does not claim a conforming implementation exists.

### S_20 `stderr`

stderr is where `spec_check` prints `file:line: message` diagnostics. A nonzero exit means a check failed.

### S_21 `Steinberg`

Steinberg is the second name in Floyd-Steinberg error diffusion. The hyphenated official designation may stay.

### S_22 `stochastic`

stochastic describes Gaussian dithering in the DOGE design notes. That method is not selected.

### S_23 `subagent`

A subagent is a tightly scoped agent used for an independent encode stream. CATE requires independent work streams with disjoint writes to run as parallel subagents.

### S_24 `subagents`

subagents is the plural. Serializing two jobs that do not share a write set is nonconforming under CATE.

### S_25 `subdirectory`

A subdirectory is a nested folder. Numbered specifications MUST NOT live in a subdirectory. They live at the repository root.

### S_26 `submodule`

A submodule is a Form 1 git pin of publisher canonical git under `ref/`. SemVer is the example in this repository.

### S_27 `submodules`

submodules is the plural. Form 2 pins are not submodules. They are ordinary files with a `SOURCE.md` record.

### S_28 `subpixel`

subpixel rendering is a display technique. DOGE still permits only the eight palette colors, not extra shades from subpixel tricks.

### S_29 `Supercompiler`

Supercompiler is the last word of Surmount Systems Smart Symbolic Supercompiler. SSSSS is specification 0004, not 0003.

### S_30 `Surmount`

### S_31 `SVG`

### S_34 `synonymy`

## T

### T_1 `th`

### T_2 `TOC`

TOC is a table of contents heading. This file's table of contents links only letters that have entries.

### T_3 `toc`

toc in lowercase is the same phrase as a common noun. It is a distinct aspell token from `TOC`.

### T_4 `Tokelau`

Tokelau is a residual jurisdiction named in `0009_PDOSS.md`.

### T_5 `tokenize`

tokenize means splitting text into tokens. SSSSS encodes programs as sequential language runs of WordID values, not as hashed strings as primary identity.

### T_6 `tokenized`

tokenized is the past form. A language run is a LanguageID plus a tokenized WordID list.

### T_7 `tokenizer`

A tokenizer produces those tokens. Primary identity remains sequential LanguageID and WordID, not a hash of tokenizer output.

### T_8 `tokenizes`

tokenizes is the present form. The hashing ban in SSSSS is a requirement on identity, not a ban on having a tokenizer.

### T_9 `TOML`

TOML is the format of `lean/lakefile.toml`. Lean and YAML may indent with spaces. Numbered specifications still use tabs.

### T_10 `Transnistria`

Transnistria is a residual jurisdiction named in `0009_PDOSS.md`.

### T_11 `trie`

A trie is the ordered tree beastdb uses. A conforming implementation uses tries that do not use locks. This document does not claim those tries are implemented.

### T_12 `tries`

tries is the plural. Progress of a reader or writer MUST NOT depend on another thread being scheduled to release a mutual exclusion lock on that trie.

### T_13 `TT`

TT is type theory, as in the Idris 2 core TT based on quantitative type theory. It is not a second name for Systems Lean.

### T_14 `TUI`

TUI is a text user interface. DOGE mapping to ECMA-48 SGR is for terminals as well as graphical interfaces.

### T_15 `Turing`

Turing complete is the class of programming languages SSSSS translates among. Natural language translation is separate and is best effort unless Lean proven or high confidence.

### T_16 `txt`

txt is the extension of `aspell_words.txt` and of the RFC 2119 Form 2 pin `rfc2119.txt`.

### T_17 `typecheck`

typecheck is a single word in this list for the act of typechecking. A bootstrapped Slake that fully typechecks is a required Systems Lean validation step.

### T_18 `typechecking`

typechecking is the gerund. Saying `fully type checking` as two leftover words is nonconforming under CATE. The rephrased form is a bootstrapped Slake that fully typechecks.

### T_19 `typechecks`

typechecks is the verb form used in that rephrased requirement.
