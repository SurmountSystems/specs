# Concise American Technical English (CATE)

> v1.1.0 - 20260825

> Technical English for numbered Surmount specifications and for agents that encode them

## 1. Scope

This document specifies Concise American Technical English (CATE) for numbered specifications in this repository and for agents that encode or revise those specifications.

This specification is number 0005. The file name is `0005_CATE.md`.

CATE is not specification 0006. Number 0006 is Recursive Self Improvement (`0006_RSI.md`). CATE is not an extension clause of `0000_spec.md`. Form rules remain `0000_spec.md`. Authors SHALL follow this specification when writing numbered specifications in this repository.

This document is the contract that humans read. It does not contain Lean theorem statements. Selected checkable claims have a companion Lean model under `lean/` (see Clause 1.2). That model is not this specification.

This document does not claim that every agent already conforms. This document does not claim that a conforming product exists.

## 3. Definitions

### 3.1 CATE

Concise American Technical English as specified by this document.

### 3.2 Complete thought

A sentence or question that states a full idea in ordinary American English. A half label used as if it were a sentence is not a complete thought.

### 3.3 Half label

A fragment that names a topic without stating a complete American English thought (for example a short caption used as if it were a question to a human).

### 3.4 Leftover unstack

The result of deleting a hyphen from a compound of the kind used in legal captions and leaving the same two words. Leftover unstack is nonconforming. Rephrasing into ordinary English is conforming.

### 3.5 Leftover unstack floor list

The phrases Lean `spec_check` flags in numbered specification prose outside fenced code and outside inline code. The list is a floor, not a complete English checker. Authors still SHALL rephrase other leftover pairs the checker does not name. The current floor list is:

```text
non markdown
must like
LF only
lock free tries
fully type checking
```

### 3.6 Residual record

A record on disk that names unpublished specifications, unassigned numbers, unpinned prior art, unimplemented requirements, and out of scope items the document names. A parenthetical planned file name in Scope is not a residual record. Silence about residual is nonconforming when those items are named.

### 3.7 Encode effort

The work of writing or revising a numbered specification in this repository, including form, Lean meaning model, registry, residual, README, and the Nix flake check.

### 3.8 Independent work streams

Two or more encode jobs that do not share a write set. They SHALL run as parallel subagents. Serializing them without a shared write set is nonconforming.

### 3.9 Requirement keywords

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY, and OPTIONAL in this document are to be interpreted as described in RFC 2119.

### 3.10 Decoder ring jargon

Private labels that force the reader to decode a nickname instead of naming the real file, clause, product, or outcome.

## 4. Core requirements

### 4.1 Complete American English thoughts

1. Authors SHALL write complete American English thoughts.
2. Authors SHALL NOT use half labels as sentences.
3. Complete sentence quality beyond the leftover unstack floor list and the Residual heading check is not fully mechanical. Authors still SHALL write complete American English thoughts.

### 4.2 Questions to humans

1. A question to a human SHALL name the file or clause.
2. A question to a human SHALL quote the current wording.
3. A question to a human SHALL say why the choice matters.
4. A question to a human SHALL name the options.
5. A question to a human SHALL use ordinary English.
6. When a question introduces a new phrase, it SHALL define that phrase in the same sentence.
7. A question to a human SHALL say what we will do for each option.
8. A half label is not a complete question.

### 4.3 Concise prose

1. Prefer one idea per sentence when that stays clear.
2. Authors SHALL NOT use decoder ring jargon.
3. Authors SHALL name the real thing: the file, the clause, the product, the checker, or the outcome.

### 4.4 Hyphenation and leftover unstack

1. Hyphenated compounds of the kind used in legal captions SHALL be rephrased into ordinary English as in `0000_spec.md` Clause 7.
2. Authors SHALL NOT delete the hyphen and leave the same two words. That leftover unstack is nonconforming.
3. The Lean `spec_check` program SHALL flag the leftover unstack floor list (Clause 3.5) in numbered specification prose outside fenced code and outside inline code.
4. The leftover unstack checker SHALL NOT flag `high assurance`, `3 bit`, or `time series` merely for having a space. `high assurance` may stay when it already reads as English.
5. Authors still SHALL rephrase other leftover pairs the checker does not name.

### 4.5 Residual in full

1. Residual SHALL be written in full on disk when the document names unpublished specifications, unassigned numbers, unpinned prior art, unimplemented requirements, or out of scope items.
2. A parenthetical planned file name in Scope is not enough.
3. For numbered specifications other than `0000_spec.md` (0001 and later published numbers), if the file contains a `NNNN_descriptive.md` token whose registry row is unpublished or planned, the file SHALL include a markdown heading titled Residual (for example `## 6. Residual`).
4. `0000_spec.md` is exempt from that heading check because it is the form spec and may cite later specifications.
5. Silence about residual is nonconforming.

### 4.6 Spec markdown and Lean

1. Numbered markdown is the contract that humans read.
2. Lean is a separate model of selected clauses.
3. Meaning proofs SHALL NOT be treated as a second markdown form checker.

### 4.7 No invented conforming product

1. Authors SHALL NOT claim that a conforming product exists unless the repository operator has said that product exists.

### 4.8 RFC 2119 is not replaced

1. CATE SHALL NOT replace RFC 2119.
2. Requirement keywords remain as in `0000_spec.md` Clause 4 and RFC 2119.

### 4.9 Independent work streams as parallel subagents

1. Independent work streams SHALL run as parallel subagents.
2. Authors SHALL NOT serialize two jobs that do not share a write set.
3. When two specifications must land in one effort, spawn one subagent per specification on disjoint files, then one pass on shared files (registry, README, `AGENTS.md`, residual, flake).

### 4.10 Self improvement of the encode process

1. When friction appears in the same encode effort (hyphen leftovers, incomplete questions, README wording that does not match the registry), authors SHALL improve the encode process in that same effort.
2. Authors SHALL prove that improvement with a Lean check or a skill step, not a chat reminder.

### 4.11 Size reports and git status

1. When the operator asked for size, authors SHALL run `scc --exclude-dir ref,.git,result,lean/.lake,.direnv --exclude-ext pdf .` before and after, including the COCOMO block.
2. COCOMO is fun and is not a real cost or schedule. Authors SHALL NOT pass `--no-cocomo`.
3. When the operator asked for git status, authors SHALL run `git status --short`.
4. Authors SHALL NOT run `git add` or `git commit` unless the operator explicitly asked for that git work.
5. Git remains forbidden in this repository unless the operator explicitly asked for that git work.

## 5. Conformance

A numbered specification document conforms to this specification if and only if all of the following hold:

1. It uses complete American English thoughts and does not use half labels as sentences (Clause 4.1).
2. Every question to a human names the file or clause, quotes the current wording, says why the choice matters, names the options, uses ordinary English, defines a new phrase in the same sentence when one is introduced, and says what we will do for each option (Clause 4.2).
3. Prose is concise, names the real thing, and does not use decoder ring jargon (Clause 4.3).
4. Hyphenated compounds of the kind used in legal captions are rephrased; leftover unstack is absent from numbered specification prose outside fenced code and inline code; `high assurance`, `3 bit`, and `time series` are not treated as leftover unstack merely for having a space (Clause 4.4).
5. Residual is written in full on disk when the document names unpublished specifications, unassigned numbers, unpinned prior art, unimplemented requirements, or out of scope items; a numbered specification other than 0000 that contains a planned or unpublished `NNNN_*.md` token includes a Residual heading (Clause 4.5).
6. Numbered markdown is treated as the contract humans read, and Lean meaning proofs are not treated as a second markdown form checker (Clause 4.6).
7. It does not claim that a conforming product exists unless the repository operator has said that product exists (Clause 4.7).
8. It does not replace RFC 2119 or invent a private mapping that weakens RFC 2119 keywords (Clause 4.8).

An encode effort in this repository conforms to this specification if and only if all of the following hold, in addition to items 1 through 8 of this clause as they apply to the effort:

1. Independent work streams run as parallel subagents on disjoint write sets (Clause 4.9).
2. Friction in the same encode effort improves the encode process, proved with a Lean check or a skill step (Clause 4.10).
3. Size reports include COCOMO when the operator asked for size, and git status is `git status --short` when the operator asked for git status, without `git add` or `git commit` unless the operator asked (Clause 4.11).

This specification is not itself a conforming implementation of a product. Meeting these items is a claim about a document or an encode effort, not about this markdown file as a shipped engine.

Optional recommendations (SHOULD, RECOMMENDED) do not break conformance when unmet, but authors SHOULD follow them unless there is a clear reason not to.
