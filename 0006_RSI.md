# Recursive Self Improvement

> v0.1.0 - 20260831
>
> A skill, a philosophy, and possible later input to the Surmount Systems System Prompt

## 1. Scope

This document specifies Recursive Self Improvement (RSI) for Surmount numbered specifications and for agents that encode or revise those specifications. RSI is a skill, a philosophy, and possible later input to the Surmount Systems System Prompt (SSSP). SSSP has no assigned specification number. This document does not create a numbered file for SSSP.

Recursive self improvement in this specification is the loop of durable tools, failing tests first, honest residual, parallel independent streams, and asking when intent is ambiguous. It is not a claim that a model trains itself again in this repository.

This document is the contract that humans read. It does not contain Lean theorem statements. Selected checkable claims have a companion Lean model under `lean/` (see Clause 1.2). That model is not this specification.

This document does not claim that every agent already conforms. `bitmask-core`, `bitmask-next`, and RGB are not Surmount numbered specifications. This document does not create a numbered file for them. Lean Machine is specified in `0013_Lean_Machine.md`.

Mentions of a remote builder or of tests that compile are practice for proving those tests when a project already requires that builder. They are not a specification of any product tree outside this repository. They are not a specification of bitmask products.

## 3. Definitions

### 3.1 RSI

The Recursive Self Improvement specified by this document. The short name is the three ASCII letters R, S, I.

### 3.2 Durable tool

A Lean checker, a project skill, a Nix package, or another maintained artifact that a later session can run. A chat reminder is not a durable tool.

### 3.3 Disposable job

Work done once as a throwaway script or a throwaway probe that is not kept as a durable tool.

### 3.4 Tool factory

Use of a large language model to produce or improve a durable tool when a job will repeat, rather than only to perform that job once.

### 3.5 Named contract

The intended behavior a test encodes, written in ordinary English. When that contract changes, the numbered specification that states it MUST change in the same effort. When RSI is that specification, this document MUST change.

### 3.6 Failing test first

The proof order in which authors and agents observe a failing test in the product tree for the named contract before the product edit that is meant to make that same test pass.

### 3.7 Remaining work pointer

A complete American English record on disk of what is still owed, written so the next session can continue without reconstructing intent from chat.

### 3.8 Independent work stream

A job that does not share a write set with another job that is live in the same effort.

### 3.9 Disjoint write set

A set of files one stream may change that does not overlap the set another live stream may change. Files that more than one stream must change are a shared write set.

### 3.10 Tightly scoped agent

An agent given one independent work stream, a bounded write set, and a short report path. This document does not name a host product for spawning agents.

### 3.11 SSSP

The Surmount Systems System Prompt. This document names SSSP as possible later input. SSSP has no assigned specification number. This document does not create a numbered file for SSSP.

### 3.12 Remote builder

A machine other than the author's laptop that already compiles and runs tests for a project when that project requires it. This document does not name a host. `bitmask-next` is not a Surmount numbered specification. This document does not create a numbered file for it.

### 3.13 Best available tool

The tool that can state the theorem or the contract with the strongest honest check among tools that actually exist for that job. Language purity is not the reason to pick it.

### 3.14 Recursive self improvement loop

The loop this specification names: improve durable tools, prove them with failing tests first, keep residual honest on disk, run independent streams in parallel, and stop to ask when intent is ambiguous. It is not a training run stored in this tree.

### 3.15 Maximal truth seeking

Proving assumptions, naming what was ruled out, and refusing to present leftover guesses as findings.

### 3.16 Leftover unstack

Deleting a hyphen and leaving the same two words. Leftover unstack is nonconforming under `0005_CATE.md`. This document does not replace CATE.

### 3.17 CATE

Concise American Technical English, specified in `0005_CATE.md`. CATE is specification 0005. CATE is not specification 0006.

### 3.18 Systems Lean

The language specified in [0002_Systems_Lean.md](0002_Systems_Lean.md): Lean 4 with linear and affine ownership and Quantitative Type Theory multiplicities 0, 1, and omega.

### 3.19 Slake

The compiler specified in [0002_Systems_Lean.md](0002_Systems_Lean.md): the compiler written in Systems Lean that emits freestanding products.

### 3.20 beastdb

The durable ordered store specified in [0003_beastdb.md](0003_beastdb.md). The product name is the lowercase form beastdb.

### 3.21 SSSSS

The Surmount Systems Smart Symbolic Supercompiler specified in [0004_SSSSS.md](0004_SSSSS.md).

### 3.22 CompCert C

C compiled by CompCert (`ccomp`) such that the generated assembly is the CompCert verified compilation of that C, as defined in [0002_Systems_Lean.md](0002_Systems_Lean.md) when that substrate is the home of that tool.

### 3.23 Scripture naming

The informative naming in Clause 1.4. It is not a conformance item.

### 3.24 Requirement keywords

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY, and OPTIONAL in this document are to be interpreted as described in RFC 2119.

### 3.25 Same word, different trees

The same English word can name different things in this repository, in Systems Lean, and in companion Lean. Those uses SHALL NOT be treated as the same fact.

1. Systems Lean (Clause 3.18) is the language. Slake (Clause 3.19) is the compiler. The Lake package id `SystemsLean` in the product tree is an internal identifier. It is not a second language name. Prose SHALL say Systems Lean or Slake, not that package id, when naming the language or the compiler.
2. The numbered markdown at the repository root is the specification people read. Companion Lean under `lean/` is a meaning model of selected claims. Lean `spec_check` is the form checker. Those three artifacts SHALL NOT be treated as one another. Meaning proofs MUST NOT be treated as a second markdown form checker (Clause 1.2).
3. Residual in this specification is remaining work written in full on disk (Clause 3.7). Residual in `0002_Systems_Lean.md` is a named fact that keeps a product from being fully freestanding. A product tree claim that a freestanding release has no managed Lean leftover is a third use of the word. Those three uses SHALL NOT be treated as the same fact. That product tree claim SHALL NOT be read as this specification having no remaining work.
4. The companion Lean meaning model is not a machine learning training run. Recursive self improvement is the loop in Clause 3.14. It is not a claim that a model trains itself again in this repository (Clause 4.6).
5. Leftover unstack (Clause 3.16) is specified by CATE in `0005_CATE.md`. This document does not replace that repair. Leftover unstack remains nonconforming.
6. The ASCII word omega in prose is the unrestricted Quantitative Type Theory multiplicity in `0002_Systems_Lean.md`. The companion Lean constructor for that multiplicity is named unrestricted. Authors SHALL NOT write a Greek letter for that multiplicity in this document.
7. Scripture named in Clause 1.4 is not a conformance item for Slake, beastdb, or SSSSS (Clause 4.9).
8. Independent work streams with disjoint write sets SHALL run as parallel tightly scoped agents (Clause 4.7). Running those jobs one after another does not conform.
9. Tests are named contracts (Clause 3.5). Observing a failing test for that contract and then editing the product conforms (Clause 4.3). Editing the product and then reshaping the test so it passes without a contract change does not conform.
10. This specification is number 0006. CATE is specification 0005 (Clause 1.1 item 4).

## 4. Core requirements

### 4.1 Tools that build tools

1. Agents SHALL prefer improving durable tools (Clause 3.2) over performing a repeated job as a disposable job (Clause 3.3).
2. When a job appears more than once, large language models SHALL be used as tool factories (Clause 3.4): they SHALL produce or improve a durable tool, not only perform the job once.
3. Durable tools in this repository SHALL be Lean checkers, project skills, or Nix packages when those can state the check. A probe that is thrown away after one use is not that tool.
4. When the encode process itself is improved in the same effort, a Lean checker, a skill step, or a Nix package that proves the improvement is REQUIRED. A chat reminder is not that proof.
5. Authors SHALL NOT invent a new Python script or a new shell script as check policy when a Lean checker or a pure Nix evaluation check can state the same rule.

### 4.2 Best tool with reason

1. Language purity is not ideology. Authors and agents SHALL use the best available tool that can state the theorem or the contract (Clause 3.13).
2. When that substrate exists, that tool MAY be CompCert C (Clause 3.22), Rust, or Systems Lean as specified in `0002_Systems_Lean.md`.
3. Authors SHALL NOT use bash or Python as check policy in Nix. Form rules for numbered specifications remain Lean `spec_check`. Trailing whitespace and tab indent across this repository remain pure Nix evaluation as in `0000_spec.md` Clause 17.1.
4. Authors and agents SHALL discard a broken tool rather than keep it because it is familiar.
5. When a stronger tool can state the theorem, authors SHALL use that tool. They SHALL NOT fall back to a weaker testing workflow because it is familiar or looks smaller.

### 4.3 Failing tests first

1. For behavior changes and bug fixes, authors and agents SHALL observe a failing test in the product tree for the named contract (Clause 3.5) before the product edit that is meant to make that same test pass (Clause 3.6).
2. Tests are contracts. When the intended contract changes, authors SHALL reconcile that change with the numbered specification in the same effort. When RSI is the specification that changed, they SHALL reconcile with this document.
3. Authors SHALL NOT reshape a test so it passes without a contract change.
4. Authors SHALL NOT delete or weaken a test to finish green when the named contract has not changed.
5. Green without a prior observed failing test for that named contract is not the proof order this clause requires.

### 4.4 Ambiguity and truth seeking

1. When intent is ambiguous, authors and agents SHALL stop and ask in ordinary American English.
2. A question to a human SHALL name the file or clause, quote the current wording, say why the choice matters, name the options, use ordinary English, define a new phrase in the same sentence when one is introduced, and say what we will do for each option, as required by `0005_CATE.md`.
3. Authors and agents SHALL prove assumptions. They SHALL NOT rely on unstated heuristics.
4. Authors and agents SHALL seek the truth of the work (Clause 3.15). They SHALL NOT pad an unknown with leftover guesses presented as findings.
5. When they do not know why something fails, they SHALL say they do not know, name what they ruled out, and ask for the fact that would distinguish remaining causes.

### 4.5 Attention and remaining work

1. Authors and agents SHALL plan with pointers on disk: residual clauses, `RESIDUAL.md`, reports under the operator report home, and project skills.
2. Remaining work SHALL be written in full in complete American English sentences (Clause 3.7). Chat is not the residual record.
3. A later session SHALL be able to continue from those pointers without reconstructing intent from chat.
4. Prose SHALL be concise natural language. Authors SHALL NOT use decoder ring jargon. Help the next session.
5. Silence about unpublished specifications, unassigned numbers, unpinned prior art, unimplemented requirements, or out of scope items this document names is nonconforming for this specification as a document. Residual is Clause 6.

### 4.6 Self improvement loop

1. Recursive self improvement in this specification is the loop in Clause 3.14: improve durable tools, prove them, keep residual honest, run independent streams in parallel, and ask when intent is ambiguous.
2. This specification MUST NOT be read as a claim that a model trains itself again in this repository.
3. Inference that tests training, in the sense of this document, is that loop. It is not a training run stored in this tree.
4. This document MAY later be input to SSSP (Clause 3.11). SSSP has no assigned specification number. This document MUST NOT be read as creating SSSP.

### 4.7 Parallel independent streams

1. Independent work streams (Clause 3.8) SHALL run as parallel tightly scoped agents (Clause 3.10) when those streams do not share a write set (Clause 3.9).
2. Authors and agents SHALL NOT run two jobs one after the other when those jobs do not share a write set.
3. When two numbered specifications must land in one effort, authors SHALL spawn one tightly scoped agent per specification on disjoint files.
4. Files that more than one stream must change SHALL be updated in one later pass, not raced by parallel writers.
5. A new ask that does not share a write set with a healthy live stream SHALL run in parallel. It SHALL NOT cancel that live stream unless the operator said to stop.

### 4.8 Remote builder practice

1. When this document talks about proving tests that compile, those tests SHALL run on a remote builder if the project already requires that builder (Clause 3.12).
2. If that builder is unresponsive, authors and agents SHALL stop rather than invent a weaker local compile as the proof.
3. This specifications repository's validation gate remains `nix flake check` as in `0000_spec.md`. That gate is not a Rust cargo harness.
4. `bitmask-core`, `bitmask-next`, and RGB are out of scope as product. This document SHALL NOT treat those trees as deliverables.
5. Practice about a remote builder is not a specification of bitmask products. This document SHALL NOT be read as a bitmask specification.

### 4.9 Scripture is not a compiler test

1. Scripture named in Clause 1.4 MUST NOT be a conformance item for Slake, beastdb, or SSSSS.
2. An implementation MUST NOT be judged conforming or nonconforming by citation of scripture.
3. Authors SHALL NOT expand Clause 1.4 into theology in this document or in a later numbered specification without an explicit operator ask.
4. The informative naming in Clause 1.4 MUST NOT be treated as a proven cosmology.

### 4.10 Same word, different trees

1. Authors and agents SHALL keep the distinctions in Clause 3.25 when the same English word appears in more than one tree.
2. Authors SHALL NOT treat Systems Lean, Slake, and the Lake package id `SystemsLean` as one name.
3. Authors SHALL NOT treat the numbered markdown, the companion Lean meaning model, and `spec_check` as one artifact.
4. Authors SHALL NOT treat remaining work on disk, a named freestanding blocker in Systems Lean, and a product tree claim that a freestanding release has no managed Lean leftover as one residual fact.
5. Authors SHALL NOT treat the companion Lean meaning model as a machine learning training run.
6. Authors SHALL NOT replace leftover unstack as specified in `0005_CATE.md`.
7. Authors SHALL write the unrestricted multiplicity as the ASCII word omega in prose. They SHALL name the companion Lean constructor unrestricted.
8. Independent work streams with disjoint writes MUST run in parallel. Serializing them does not conform (Clause 4.7).
9. A failing test then a product edit conforms. A product edit then reshaping the test does not conform (Clause 4.3).
10. Companion Lean under `lean/` encodes those distinctions. That encoding is a meaning model. It is not this specification.

### 4.11 Meaning models in this repository

1. Authors and agents who prove companion Lean meaning models under `lean/` in this repository SHALL follow the project skill `/lean4` at `.agents/skills/lean4/SKILL.md`.
2. That skill points at the Lean 4 agent skill pack git submodule at `skills/lean4-skills`. That pack is not a Clause 12 pin. That pack is not under `ref/`. That pack is not `mathlib`.
3. This Lake package SHALL NOT add `mathlib`.

## 5. Conformance

Work in this repository conforms to this specification if and only if all of the following hold:

1. Durable tools are preferred over a disposable job when the job repeats, a repeated job is turned into or improved as a tool rather than only performed once, and an encode process improvement is proved by a Lean checker, a skill step, or a Nix package rather than by a chat reminder (Clause 4.1).
2. The best available tool that can state the theorem or the contract is used; bash and Python are not used as check policy in Nix; a broken tool is discarded; a stronger tool that can state the theorem is not skipped because a weaker workflow is familiar (Clause 4.2).
3. For behavior changes, a failing test in the product tree for the named contract is observed before the product edit that is meant to make that same test pass, and contract changes are reconciled with the numbered specification, with this document when RSI is that specification (Clause 4.3).
4. Ambiguous intent is stopped on and asked about with a question that names the file or clause, quotes the current wording, says why the choice matters, and names the options; assumptions are proved; unstated heuristics are not relied on; leftover guesses are not presented as findings (Clause 4.4).
5. Remaining work is written in full on disk in complete American English; chat is not treated as the residual record; a later session can continue from those pointers (Clause 4.5).
6. Recursive self improvement is treated as the loop in Clause 4.6, not as a claim that a model trains itself again in this repository, and this document is not treated as specifying SSSP (Clause 4.6).
7. Independent work streams that do not share a write set run as parallel tightly scoped agents; jobs that do not share a write set are not forced to wait on each other; shared files are updated in one later pass (Clause 4.7).
8. When proving tests that compile for a project that already requires a remote builder, those tests run on that builder, and work stops if that builder is unresponsive; `bitmask-core`, `bitmask-next`, and RGB are not treated as deliverables of this document (Clause 4.8).
9. Scripture named in Clause 1.4 is not treated as a conformance item for Slake, beastdb, or SSSSS, and is not treated as a proven cosmology (Clause 4.9).
10. The same English word used in more than one tree is kept distinct as in Clause 3.25 and Clause 4.10.
11. Authors and agents who prove companion Lean meaning models follow the project skill `/lean4`; this Lake package does not add `mathlib`; shipped theorems do not contain `sorry` (Clause 4.11).

The informative naming in Clause 1.4 is not a conformance item.

This specification is not itself a conforming implementation. Meeting these items is a claim about work in this repository, not about this markdown file.
