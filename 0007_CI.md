## 3. Definitions

### 3.1 Continuous Integration

The practice specified by this document: the named gate is green before commit and before push, commits are signed by the human operator except for the single named exception, and stack checks named here stay honest about what is required and what is not claimed done.

### 3.2 Named gate

The test command a project names as its validation gate. For this specifications repository the named gate is:

```text
nix flake check "path:$PWD" --print-build-logs
```

A Surmount product tree that claims this specification SHALL name its own gate in that tree. Naming a residual MUST NOT replace a red gate.

### 3.3 Red gate

A named gate that has not been run, or that has been run and has failed.

### 3.4 Green gate

A named gate that has been run and has passed.

### 3.5 Commit object

A git commit object. Agents MUST NOT create commit objects. The human operator creates commit objects.

### 3.6 Operator signature

A commit signed by the human operator with the operator's signing key, using `git commit -S` or an equivalent that produces a signature from that same key.

### 3.7 Named exception

The single exception in Clause 4.3. It applies only when a product keeps two source trees, Grok Build source that people can read and a distinct Open Source version that is published, and only when that product's residual names the unsigned history or the history signed with a different key. It is not a general license to skip signing.

### 3.8 Formal Vibefication (this repository)

The split specified in [0008_Formal_Vibefication.md](0008_Formal_Vibefication.md): numbered markdown is the contract humans read; the specification is also encoded in Lean as declarations of what must be true; proofs of those encodings live in separate Lean modules; product trees implement. Numbered markdown is not a substitute for those encodings. Lean proofs are not the specification.

### 3.9 Systems Lean product path

The path specified by [0002_Systems_Lean.md](0002_Systems_Lean.md) in which specification, proof, and implementation live in one typed language so a project can be shown logically consistent, after which Slake emits ahead of time (`AOT`) freestanding C and MAY emit optional LLVM IR. That unification is for Systems Lean product trees. It is not a license to dump theorems into numbered markdown in this specifications repository.

### 3.10 Byte identity

Exact match of bytes (and of each file as a file) among emitted C, headers, archives, shared objects, LLVM IR, `ELF`, and other intermediates that a conforming Systems Lean and Slake product emits. Byte identity is a requirement on such a product and is not claimed true ([0002_Systems_Lean.md](0002_Systems_Lean.md) Clause 6.3). This document does not claim that match already holds. Byte identity of emit remains required for a conforming product and is not claimed true. The match is pursued by delta reconciliation in [0004_SSSSS.md](0004_SSSSS.md): the same input goes to the Lean symbolic rules and to the reference compiler, both outputs are decompiled, and the deltas are labeled. A `FastC` mark does not waive the match. A user who may skip running the Slake typecheck is not excused from the match. The reference side of delta reconciliation is the major compilers. CompCert `ccomp`, `CompCertTSO`, gcc, LLVM, and `cc` are in that set, and being a reference target does not mean that compiler satisfies Clause 4.2 item 6 of [0002_Systems_Lean.md](0002_Systems_Lean.md).

### 3.11 Reality check (SSSSS and beastdb)

The check that every effort on a conforming SSSSS and beastdb stack can be compiled again by SSSSS with the same inputs, with durable state in beastdb, so the language model is checked against reality. That check is a requirement on that stack. This document does not claim SSSSS exists. This document does not claim beastdb is implemented. This document does not claim the check is done.

### 3.12 Requirement keywords

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY, and OPTIONAL in this document are to be interpreted as described in RFC 2119.

## 4. Core requirements

### 4.1 Named gate before commit and before push

1. Tests that the project names as its gate MUST be run and MUST be green before commit and before push.
2. For this specifications repository the named gate is `nix flake check "path:$PWD" --print-build-logs`.
3. A Surmount product tree that claims this specification SHALL name the command that is its gate.
4. Naming a residual MUST NOT replace a red gate.
5. A commit while the named gate is red does not conform.
6. A push while the named gate is red does not conform.

### 4.2 Signed commits and agents

1. Commits MUST be signed by the human operator with the operator's signing key (`git commit -S` or equivalent).
2. Agents MUST NOT create commit objects.
3. Unsigned commits are nonconforming except the single named exception in Clause 4.3.
4. A commit signed by a key that is not the operator's signing key does not satisfy this clause unless Clause 4.3 applies and the product residual names that different signing.

### 4.3 Named exception only

1. A product that keeps two source trees, one Grok Build tree whose source people can read and one distinct Open Source tree that is published, MAY use a documented unsigned history or a documented history signed with a different key if and only if that exception is named in residual for that product.
2. That exception MUST NOT be treated as a general license to skip signing.
3. Authors SHALL NOT expand this exception.
4. This specifications repository does not claim that exception for itself. Commits in this specifications repository remain Clause 4.2.

### 4.4 Pre-commit

1. Pre-commit MAY run the named gate.
2. Pre-commit is not a substitute for the operator signature in Clause 4.2.
3. A green pre-commit hook does not authorize an agent to create a commit object.

### 4.5 Spec, proof, and implementation in this specifications repository

1. In this specifications repository, numbered markdown, Lean spec encodings, and Lean proofs SHALL stay distinct from each other and from product implementation (Formal Vibefication, Clause 3.8, as specified in [0008_Formal_Vibefication.md](0008_Formal_Vibefication.md)).
2. Numbered markdown is the contract humans read.
3. Lean spec encodings declare what must be true. Proofs of those encodings live in separate Lean modules. Lean proofs are not the specification.
4. Product trees implement.
5. Lean 4 SHALL be used to surface logical inconsistency in the models.
6. Meaning proofs MUST NOT be treated as a second markdown form checker.
7. `spec_check` remains the form checker (ASCII, tabs, RFC 2119, spelling, leftover unstack, Residual heading, registry scan).
8. Authors SHALL NOT dump theorems into numbered markdown in this repository as a substitute for the Systems Lean product path.

### 4.6 Systems Lean product path

1. Systems Lean as specified in [0002_Systems_Lean.md](0002_Systems_Lean.md) completes the product path: specification, proof, and implementation live in one typed language so a project can be shown logically consistent, after which Slake emits ahead of time freestanding C and MAY emit optional LLVM IR.
2. That unification is for Systems Lean product trees.
3. That unification MUST NOT be read as a license to dump theorems into numbered markdown in this specifications repository.
4. This document does not replace [0002_Systems_Lean.md](0002_Systems_Lean.md).

### 4.7 Byte identity of emit

1. A conforming Systems Lean and Slake product MUST keep byte identity (Clause 3.10) among emitted C, headers, archives, shared objects, LLVM IR, `ELF`, and other intermediates it emits.
2. That requirement is a requirement on the product and is not claimed true ([0002_Systems_Lean.md](0002_Systems_Lean.md) Clause 6.3). It is not a claim that the match already holds. Byte identity of emit remains required for a conforming product and is not claimed true. The match is pursued by delta reconciliation in [0004_SSSSS.md](0004_SSSSS.md): the same input goes to the Lean symbolic rules and to the reference compiler, both outputs are decompiled, and the deltas are labeled. A `FastC` mark does not waive the match. A user who may skip running the Slake typecheck is not excused from the match.
3. Residual for this specification MUST say the match is not claimed done.
4. Companion Lean SHALL encode the requirement and the honest residual as distinct facts. Companion Lean SHALL NOT treat emit equal to `ELF` as a proved identity.

### 4.8 SSSSS and beastdb reality check

1. If every effort on a stack can be compiled again by SSSSS with the same inputs, that compilation, together with beastdb as the durable store those runs reference, is how the language model is checked against reality.
2. That check is REQUIRED for a conforming SSSSS and beastdb stack.
3. That check is not a claim that SSSSS exists.
4. That check is not a claim that beastdb is implemented.
5. Residual for this specification MUST say the check is not claimed done.

### 4.9 Rust and fargo

1. Rust SHALL be elevated with fargo, as [0002_Systems_Lean.md](0002_Systems_Lean.md) Clause 3.47 names fargo and does not assign fargo a specification number.
2. fargo has no assigned specification number, so this document does not state a fargo process. This document does not create a numbered file for fargo.
3. Residual SHALL record that fargo has no numbered specification and no assigned number.
4. Authors SHALL NOT invent a numbered specification file for fargo in this effort. Prefer residual that stays unnumbered.

## 5. Conformance

Work that claims this specification conforms if and only if all of the following hold:

1. The named gate is run and green before commit and before push; naming a residual does not replace a red gate (Clause 4.1).
2. Commits are signed by the human operator with the operator's signing key; agents do not create commit objects; unsigned commits occur only under Clause 4.3 (Clause 4.2 and Clause 4.3).
3. The named exception, when used, is named in residual for that product and is not treated as a general license to skip signing (Clause 4.3).
4. Pre-commit, when used, does not substitute for the operator signature and does not authorize an agent to create a commit object (Clause 4.4).
5. In this specifications repository, numbered markdown, Lean spec encodings, and Lean proofs stay distinct; Lean 4 surfaces logical inconsistency in the encodings and in the proofs; spec encodings of meaning are not a second form checker; `spec_check` remains form (Clause 4.5).
6. The Systems Lean product path is treated as unification in product trees, not as a license to dump theorems into numbered markdown here (Clause 4.6).
7. Byte identity of Slake emit is treated as a product requirement and is not claimed true in this document (Clause 4.7).
8. The SSSSS and beastdb reality check is treated as a requirement on that stack and is not claimed done (Clause 4.8).
9. Rust elevation uses fargo. fargo has no assigned specification number, so this document does not state a fargo process. This document does not create a numbered file for fargo (Clause 4.9).

This specification is not itself a conforming Continuous Integration product. Meeting these items is a claim about work that claims this specification, not about this markdown file as a shipped engine.

Optional recommendations (SHOULD, RECOMMENDED) do not break conformance when unmet, but authors SHOULD follow them unless there is a clear reason not to.
